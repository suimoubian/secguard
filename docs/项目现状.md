## 一、这是什么

一个用 C++20 手写 AC 自动机做核心的 Web 安全审计引擎(WAF)。
放在网站前面,检查每个进来的请求,拦住 SQL 注入 / XSS / 路径穿越 / 命令注入,
把每次检测结果写成审计日志,再把被拦下的记录交给大模型判断真假。

**它和"调个现成库"的项目区别在哪**:核心匹配算法是自己写的,
并且有数据证明它比朴素实现快 52 倍。

## 四、四个能讲的技术点

| 技术点 | 结论 | 数据 |
|---|---|---|
| **手写 AC 自动机** | 特征数 ×5,耗时 ×1.05;朴素实现 ×5.18 | 1000 条特征时快 **52.5 倍** |
| **无锁 MPSC + 批量落库** | 审计异步化 | 比同步写库快 **194 倍**(56371 vs 291) |
| **Redis 共享限流封禁** | 多实例状态一致 | 单机内存的代价:QPS 从 84654 降到 56371(1.5x) |
| **线程数必须 ≥ 连接数** | httplib 是一线程守一连接 | 线程 4→64,P99 从 289ms 降到 6ms |

### 数据口径(重要,别记错)

- 引用**保守下界**:完整检测链路 **36520 QPS / P50 1.57ms / P99 8.29ms**(2 核 64 连接)
- 复测过一轮是 56371 QPS,但**代码没变**,纯粹是机器状态差异(同场景两轮差 40% 是常态)
- 所以对外统一说"3.6 万 QPS",并主动补一句"这是我笔记本上下界,真实值要在目标机器重测"
- **绝对值不可靠,比值可靠** —— 面试优先讲上表里的倍数

## 五、已知局限(主动说,别等人问)

1. LLM 只分析被拦截的记录,规则漏掉的攻击不进队列
2. 限流按 IP,对分散 IP 的慢速攻击不敏感
3. 单机,没做分片;特征库扩到 10 万条内存会到 GB 级
4. WAF 防不住注入,真正的解是参数化查询(本项目 DAO 层已全部用预编译)
5. 特征库是手工整理的 228 条,不是从真实攻击日志挖的
6. 压测走 loopback,没有真实网络损耗
7. 白名单是"路径 + 规则"级,粒度粗
8. 告警通知尽力而为,不保证送达
9. 管理鉴权用用户名名单,改名单要重启

## 六、卡在哪:只有一件事

**没有服务器,所以没上线。**

技术上没有任何阻塞 —— 代码、镜像、部署脚本、上线清单全部就绪。
缺的是一台机器。

### 具体怎么解

买腾讯云轻量应用服务器(≈161 元/年),然后按 [上线清单.md](上线清单.md) 走。
全程约 40-60 分钟,其中一半在等编译。

关键三步别漏:

1. 控制台防火墙开 **TCP 8088**(系统里 ufw 开了没用)
2. 2G 内存先加 **2GB swap**,编译用 `--build-arg BUILD_JOBS=1`
3. 配 Docker 镜像加速,否则拉 mysql:8.0 会超时

### 另一件未完成

**LLM 只用 mock 跑过**,链路全通但没接真实模型。
有 API Key 后 10 分钟能验完:设 `SECGUARD_LLM_KEY` + `SECGUARD_LLM_PROVIDER=openai`,
把 `SECGUARD_AI_ENABLE=1`,触发一轮 `/api/analyze/run`。

| 依赖 | 版本 | 说明 |

| CMake / g++ | 3.22 / 11.4 | C++20 |
| MySQL | 8.0 | 库 `secguard`,用户 `secguard` |
| Redis | 6.0+ | 可选,没有会自动降级单机 |
| Docker + compose | 29.x / v2 | 部署用 |
| 库 | libssl-dev, libmysqlcppconn-dev, libhiredis-dev, libcurl4-openssl-dev, nlohmann-json3-dev | |

### 五条命令恢复

```bash
cd /home/smb/projects/secguard

# 1. 编译(约 2 分钟)
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build -j8

# 2. 起数据库容器(只需要 mysql + redis)
sudo docker compose up -d mysql redis

# 3. 起整套服务
sudo docker compose up -d --wait

# 4. 自检(54 项)
./scripts/verify.sh

# 5. 浏览器打开
# http://localhost:8088
```

### 两个环境相关的坑(踩过,记一下)

1. **WSL 空闲会自行关闭**,里面的容器全停。已建 `C:\Users\z\.wslconfig`
   (vmIdleTimeout)和启动文件夹里的 `secguard-wsl-keepalive.vbs` 兜住。
   换机器或重装要重做。
2. **不要连续跑多次 verify.sh,也不要在压测时跑它** —— 每轮自带 3 秒压测,
   叠加起来会把 nginx 打满,表现是一堆 502,查起来很费劲。

**最值钱的三个坑**(讲稿里有完整版):

1. **AC 自动机 insert 时持引用** —— `emplace_back` 让引用失效,段错误
2. **TLS 析构死锁** —— 连接归还给已销毁的对象,卡在 `futex_do_wait` 不动
3. **把检测挪到前置钩子,丢了整个 POST 请求体** —— 重构引入的静默功能缺失,
   而当时所有测试都是绿的(测试一直把攻击放查询串里)

## 十一、如果决定换项目

技术资产可以复用:

- `include/engine.h` + `src/engine/` 是独立的,不依赖 HTTP/数据库,可以整体搬到别的项目
- `src/db/` 的连接池 + DAO 模式、`src/cache/` 的 Redis 封装同样是通用的
- `scripts/verify.sh` 的自检思路(每组一个 PASS/FAIL,总数收口)任何项目都能用
- 踩坑记录本身是资产:**上面那三个坑,比项目本身更容易在面试里讲出深度**

一个判断:这个项目**不是被技术卡住的**,是被 161 元的采购和一小时的操作卡住的。
换项目不会让那件事消失,只是把它推迟 —— 而这个项目已经完成了 95%,
换新项目是从 0% 开始。
