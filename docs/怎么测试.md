# 怎么测试这个项目

三层,按耗时排。**第一层 60 秒,第二层 3 分钟,第三层按需挑着做。**

```bash
# 先设两个变量,后面命令都用它
BASE=http://127.0.0.1:8088        # 在服务器上测
# BASE=http://<服务器IP>:8088     # 从自己电脑测(换成你的 IP)
```

如果要从自己电脑测管理接口,需要管理员令牌:

```bash
# 在服务器上取密码
cat ~/.admin_password

# 然后换成你的
TOKEN=$(curl -s -X POST $BASE/api/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"<管理员密码>"}' | jq -r .token)
```

## 第一层:60 秒冒烟(浏览器)

打开 `http://<服务器IP>:8088`,首页有四个演示链接,依次点一遍:

| 点什么 | 期望 | 说明了什么 |
|---|---|---|
| 正常请求 | 200 | 放行 |
| 注入尝试 | 403,页面显示 `SQL-003` | 拦住了,而且告诉你命中哪条规则 |
| XSS 尝试 | 403,显示 `XSS-041,XSS-056` | 同上 |
| 路径穿越 | 403,显示 `PAT-001,PAT-012` | 同上 |

再手动敲两个地址,这两个最能体现设计:

| 地址 | 期望 | 为什么重要 |
|---|---|---|
| `/wp-login.php` | **404** | 路径不存在。但审计里**有记录** —— 扫描器最爱打不存在的地方,如果检测写在业务接口里,这些请求会静默消失 |
| `/.env` | **403** | 敏感文件探测被拦 |

一个 404 还不够,要能证明它被审计了,见第三层"未注册路径"那条。

## 第二层:3 分钟自检(一条命令)

```bash
ssh secguard
cd ~/secguard
./scripts/verify.sh
```

**52 项,12 组。全过才是环境健康的。** 它验证什么:

| 组 | 验证内容 |
|---|---|
| 0 | 自清理(脚本自己会触发限流封禁,不清会导致下一轮全红) |
| 1 | 服务活着、数据库通、Redis 通、规则库 234 条已加载 |
| 2 | 查询串检测:SQL/XSS/路径穿越/命令注入/`.env` 探测,以及正常请求不误报 |
| 3 | **请求体检测:8 个 POST 路由逐个打**,漏一个就红 |
| 4 | 未注册路径:404 但被审计 |
| 5 | 账号:注册/重名 409/弱口令 400/登录/错误口令 401/超长 id 不崩 |
| 6 | 管理鉴权:无令牌 401、普通用户 403、管理员 200 |
| 7 | 重放:同 nonce 第二次 409、过期时间戳 403 |
| 8 | 审计统计、按 IP 查 |
| 9 | AI 层:未启用时手动触发应被拒(409) |
| 10 | 热加载、白名单条数 |
| 11 | Prometheus 指标:可用、内容、数量、格式、鉴权 |
| 12 | 限流(wrk 压出 429)+ 自动封禁 + 解封恢复 |

**注意**:别和压测同时跑 —— 它自带 3 秒压测,叠加会把 nginx 打满,表现是一堆 502。

## 第三层:逐项手工验证

挑你关心的做。每条都是「命令 → 期望 → 验证点」。

### 1. 攻击检测(按类型)

```bash
curl -s -o /dev/null -w '%{http_code}\n' "$BASE/?q=union%20select%201"
```
期望 `403`。换成下面这些应当都是 403:

```bash
"$BASE/?q=1%27%20or%201=1--"                        # or 1=1
"$BASE/?q=%3Cscript%3Ealert(1)%3C/script%3E"        # XSS
"$BASE/?q=%3Cimg%20src=x%20onerror=alert(1)%3E"     # XSS 变体
"$BASE/?file=../../../../etc/passwd"                # 路径穿越
"$BASE/?cmd=;cat%20/etc/passwd"                     # 命令注入
"$BASE/.env"                                        # 敏感文件
```

**验证点**:状态码 + 响应体里的 `rule_hit` 字段说了命中哪几条规则。

### 2. 请求体检测(最容易漏的地方)

```bash
curl -s -o /dev/null -w '%{http_code}\n' -X POST "$BASE/api/check" \
  -H 'Content-Type: application/json' \
  -d '{"payload":"union select 1,2,3"}'
```
期望 `403`。

**这条必须单独测**:HTTP 库的前置钩子在读 body 之前就执行了,所以 body 是在
处理器里补扫的。曾经因为重构把这块覆盖丢了,而所有测试都是绿的
(测试一直把攻击放在查询串里)。

### 3. 正常请求不误报

```bash
curl -s -o /dev/null -w '%{http_code}\n' "$BASE/?q=hello"
curl -s -o /dev/null -w '%{http_code}\n' "$BASE/?q=this%20is%20a%20shopping%20list"
```
两个都应 `200`。第二句验证"正常文本里的常见词不触发"。

### 4. 未注册路径也被审计

```bash
curl -s -o /dev/null -w '%{http_code}\n' "$BASE/wp-login.php"   # 404
```

然后查它有没有被记录:

```bash
DBPASS=$(grep '^SECGUARD_DB_PASS=' ~/secguard/.env | cut -d= -f2-)
sudo docker exec secguard-mysql mysql -usecguard -p"$DBPASS" -e \
  "SELECT id, action, status_code, uri FROM secguard.audit_log
   WHERE uri LIKE '%wp-login%' ORDER BY id DESC LIMIT 3;"
```

**验证点**:能查到记录。这就是"检测放在路由之前"的价值 ——
如果放在业务函数里,这个请求根本不会被执行,日志一条都没有。

### 5. 账号与令牌

```bash
# 注册
curl -s -X POST "$BASE/api/register" -H 'Content-Type: application/json' \
  -d '{"username":"test001","password":"test-password-2026"}'

# 重名 -> 409
curl -s -o /dev/null -w '%{http_code}\n' -X POST "$BASE/api/register" \
  -H 'Content-Type: application/json' \
  -d '{"username":"test001","password":"test-password-2026"}'

# 弱口令 -> 400
curl -s -o /dev/null -w '%{http_code}\n' -X POST "$BASE/api/register" \
  -H 'Content-Type: application/json' -d '{"username":"weak","password":"123"}'

# 登录拿令牌
curl -s -X POST "$BASE/api/login" -H 'Content-Type: application/json' \
  -d '{"username":"test001","password":"test-password-2026"}'

# 错误口令 -> 401
curl -s -o /dev/null -w '%{http_code}\n' -X POST "$BASE/api/login" \
  -H 'Content-Type: application/json' \
  -d '{"username":"test001","password":"wrong"}'
```

### 6. 管理接口鉴权(这条最能说明"安全项目自己也安全")

```bash
# 无令牌 -> 401
curl -s -o /dev/null -w '%{http_code}\n' "$BASE/api/alerts"

# 普通用户 -> 403
UTOK=$(curl -s -X POST "$BASE/api/login" -H 'Content-Type: application/json' \
  -d '{"username":"test001","password":"test-password-2026"}' | jq -r .token)
curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $UTOK" "$BASE/api/alerts"

# 管理员 -> 200
curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $TOKEN" "$BASE/api/alerts"
```

三个数字分别是 **401 / 403 / 200**。

**为什么重要**:这些接口原来全是裸的,谁都能把告警标成"误报"—— 等于让攻击者
自己删证据。这是上线前修掉的真漏洞。

### 7. 重放防护

```bash
NOW=$(date +%s); NONCE="test-$RANDOM"
for i in 1 2; do
  curl -s -o /dev/null -w '%{http_code} ' -X POST "$BASE/api/check" \
    -H 'Content-Type: application/json' \
    -H "X-Timestamp: $NOW" -H "X-Nonce: $NONCE" -d '{"payload":"hi"}'
done; echo
```
期望 `200 409` —— 第一次过,第二次被认作重放。

### 8. 限流

```bash
wrk -t2 -c20 -d3s "$BASE/api/rules"
```
看输出里的 `Non-2xx or 3xx responses` —— 非零说明限流生效了。

串行 curl 测不出来:每次十几毫秒,追不上令牌桶的补充速度。

### 9. 自动封禁

```bash
# 连发攻击直到触发阈值(默认 20 次/5 分钟)
for i in $(seq 1 12); do curl -s -o /dev/null "$BASE/?q=union%20select%201"; done
for i in $(seq 1 12); do curl -s -o /dev/null "$BASE/?q=union%20select%202"; done

# 然后正常请求也被拦
curl -s -o /dev/null -w '%{http_code}\n' "$BASE/?q=hello"     # 403
```

**测完记得解封**,否则你自己被锁:

```bash
sudo docker exec secguard-redis sh -c \
  'for p in "sg:ban:*" "sg:hit:*"; do for k in $(redis-cli --scan --pattern "$p"); do redis-cli DEL "$k" >/dev/null; done; done'
```

或用 `./scripts/demo-attack.sh --reset`。

### 10. 白名单(证明"该放行的能放行")

在 `~/secguard/rules/allowlist.conf` 末尾加一行(用 TAB 分隔):

```
/api/check	SQL-003
```

重新加载并验证:

```bash
curl -s -X POST -H "Authorization: Bearer $TOKEN" "$BASE/api/rules/reload"

# 这个路径上 select 放行了 -> 200
curl -s -o /dev/null -w '%{http_code}\n' -X POST "$BASE/api/check" \
  -H 'Content-Type: application/json' -d '{"payload":"select * from user"}'

# 别的路径上同样的词仍然拦 -> 403
curl -s -o /dev/null -w '%{http_code}\n' "$BASE/?q=select%20*%20from%20user"

# 组合规则不受影响 -> 403
curl -s -o /dev/null -w '%{http_code}\n' -X POST "$BASE/api/check" \
  -H 'Content-Type: application/json' -d '{"payload":"union select 1"}'
```

**验证点**:同一个词,在免检路径上 200,在别的路径上 403 ——
白名单是「路径 + 规则」级,不是全局关掉某条规则。

测完把那行删掉再 reload。

### 11. 规则分级 BLOCK / ALERT

```bash
# 这个请求命中 SQL-003(ALERT 级)-> 200,但审计里是 ALERT 不是 PASS
curl -s -o /dev/null -w '%{http_code}\n' "$BASE/?q=1%20and%20(select%20count(*)%20from%20user)"

DBPASS=$(grep '^SECGUARD_DB_PASS=' ~/secguard/.env | cut -d= -f2-)
sudo docker exec secguard-mysql mysql -usecguard -p"$DBPASS" -N -e \
  "SELECT action, status_code, rule_hit FROM secguard.audit_log
   ORDER BY id DESC LIMIT 3;"
```

**这不是漏洞,是策略**:`select` 太容易误伤(技术文档里有),所以降成
"记录但不拦"。降级之后正常请求被真正拦掉的比例从 21.2% 降到 3.8%,
而攻击拦截一条没少。详见 [演示素材.md](演示素材.md)。

### 12. AI 分析层

```bash
# 一发攻击 + 触发分析
curl -s -o /dev/null "$BASE/?q=union%20select%201"
sleep 2
curl -s -X POST -H "Authorization: Bearer $TOKEN" "$BASE/api/analyze/run" | jq

# 看告警(理由应该是真实模型输出,不是 "[mock]" 开头)
curl -s -H "Authorization: Bearer $TOKEN" "$BASE/api/alerts?limit=1" | jq '.items[0].reasoning'
```

**验证点**:`calls` 和 `ok_calls` 增长、`transport_errors` 为 0、
`reasoning` 是通顺的中文分析,且会提到 `params_digest` 重复、接口分布这类
规则引擎表达不了的东西。

### 13. 监控指标

```bash
curl -s -H "Authorization: Bearer $TOKEN" "$BASE/metrics" | head -30
```

27 个指标。重点看:

| 指标 | 关心什么 |
|---|---|
| `secguard_requests_total` / `_blocked_total` | 拦截比例 |
| `secguard_audit_dropped_total` | **不为 0 说明审计在丢数据** |
| `secguard_redis_up` / `secguard_guard_mode_redis` | 0 表示降级成单机了 |
| `secguard_ai_call_errors_total` | LLM 调用失败 |
| `secguard_db_pool_idle` | 连接池是否被占满 |

### 14. 数据库压力

```bash
DBPASS=$(grep '^SECGUARD_DB_PASS=' ~/secguard/.env | cut -d= -f2-)
sudo docker exec secguard-mysql mysql -usecguard -p"$DBPASS" -e \
  "SELECT COUNT(*) AS rows_total FROM secguard.audit_log;
   SELECT action, COUNT(*) FROM secguard.audit_log GROUP BY action;"
```

审计表是"每请求一行",压测 3 分钟能写 300 万行。内置保留策略(默认 7 天)
会自动清理,配置项 `SECGUARD_AUDIT_RETENTION_DAYS`。

## 压测

```bash
cd ~/secguard
./bench/run.sh
```

自动绑核、停干扰容器、跑五组场景、输出对比表。**大约 5-8 分钟。**

**注意**:这台机器是 2 核共享型,而且 3Mbps 带宽会把"从外网压"的数字卡死
(375KB/s ÷ 1KB ≈ 375 QPS)。所以压测必须在**服务器本机**跑 loopback,
不能从家里打公网 IP。

## 常见现象怎么解释

| 现象 | 是问题吗 | 原因 |
|---|---|---|
| 某个注入返回 **200** | 通常不是 | 可能命中的是 ALERT 级规则。去审计表看 `action`,是 `ALERT` 就正常 |
| 大量 **429** | 不是 | 限流生效了。默认每 IP 50/秒、突发 100 |
| 突然全部 **403** | 不是 | 你可能触发了自动封禁(20 次/5 分钟)。等 5 分钟或手动清 `sg:*` |
| **502** | 有问题 | nginx 连不上 app。看 `docker compose ps` 和 `logs app` |
| 管理接口 **401** | 不是 | 没带令牌。管理员用户名必须在 `.env` 的 `SECGUARD_ADMIN_USERS` 里 |
| 管理接口 **403** | 不是 | 令牌有效但用户名不在管理员名单 |

## 测完之后:恢复干净状态

```bash
# 1. 清掉封禁/计数/令牌桶
./scripts/demo-attack.sh --reset

# 2. 如果改过 allowlist 或 policy,还原
cd ~/secguard && git checkout rules/allowlist.conf rules/policy.conf 2>/dev/null

# 3. 跑一遍自检确认没改坏
./scripts/verify.sh
```
