| `180.168.188.102` | 26 | **我自己的公网 IP**,从本地机器验证外网可达时打的 |
| 5 个陌生 IP | 6 | 见下表,**没有一条是攻击** |

那 6 条陌生请求的原文:

| 请求 | 结果 | 是什么 |
|---|---|---|

### 这意味着什么

| 是真的 | 不是真的 |
|---|---|
| 请求真的被扫描、被拦、被审计 | 没有真实攻击者 |

### 面试被问到怎么说

不要遮掩,直接说清楚——**这反而是加分项**:

> "这些数据是我自己压出来的,不是真实攻击。作品集项目没有真实用户,
> 谁的项目都一样。我能保证的是**技术链路是真的**:请求真的被扫、被拦、
> 落库、调模型,不是画出来的。
>
> 我没有真实对抗数据,所以我不知道真实攻击者的手法分布,也不知道在真实
> 流量下的误报率是多少。这个边界我写在文档里了。
>
> 但有一件事我做了:我没有对着'能拦住'这个感觉拍脑袋,而是自己造了 169 条
> 标注语料,量出变形攻击有 61% 能绕过 —— **即使是自己造的语料,也比'我觉得没问题'强**。"

### 想拿到真实流量怎么办

公网服务器被扫描是常态,但现在还没有——原因很简单:

- 服务开在 **8088**,通用扫描器主要扫 80/443
- 上线才 8 小时,还没被扫到

两个办法(都不难,但要接受代价):

| 办法 | 做法 | 代价 |
|---|---|---|
| 换到 80 端口 | 改 `SECGUARD_HTTP_PORT=80`,防火墙放行 80 | 未备案机器有些厂商会限制 80;会立刻开始收到大量扫描 |
| 等 | 什么都不做,过几天自然会有爬虫和扫描器 | 慢,而且量不稳定 |

> 注:用 IP 直接访问不需要备案(备案是针对域名解析的),所以 `http://IP/` 在
> 80 端口是可行的。但有些云厂商对未备案实例的 80 端口有策略限制,要试才知道。

## 一、这个项目演示什么

一条完整的链路:

```
攻击请求 -> 规则拦截(403) -> 审计落库 -> AI 二次判定(真模型) -> 告警
```

九个请求,八拦一记,然后 AI 从这批记录里读出一个"扫描器行为"的结论。

## 二、演示攻击的输出(原文)

```
$ ./scripts/demo-attack.sh http://127.0.0.1:8088

=== 发送演示攻击(共 8 次)===
  拦截  HTTP 403  /?q=union%20select%201,2,3                   SQL 注入:union select
  拦截  HTTP 403  /?q=1%27%20or%201=1--                        SQL 注入:or 1=1
  放行  HTTP 200  /?q=1%20and%20(select%20count(*)%20from%20user) 子查询(命中 SQL-003,ALERT 级)
  拦截  HTTP 403  /?q=%3Cscript%3Ealert(1)%3C/script%3E        XSS:script 标签
  拦截  HTTP 403  /?q=%3Cimg%20src=x%20onerror=alert(1)%3E     XSS:onerror 事件
  拦截  HTTP 403  /?file=../../../../etc/passwd                路径穿越:/etc/passwd
  拦截  HTTP 403  /?cmd=;cat%20/etc/passwd                      命令注入:cat
  拦截  HTTP 403  /.env                                        敏感文件探测:.env

=== 再补一条请求体攻击(POST body 里的注入)===
  HTTP 403  POST /api/check (body 里带注入)
```

### 那个 200 必须主动解释(否则会被当成漏洞)

它不是漏报。审计表里记着:

```
id     action   status_code   命中规则
1212   ALERT    200           SQL-003
1210   BLOCK    403           SQL-001,SQL-003,SQL-042
```

`SQL-003`(裸 `select ` 关键词)在 `rules/policy.conf` 里被**降级成 ALERT** ——
因为它误伤太多(技术文档、博客正文、SQL 教程里都有 `select`)。

**ALERT 的含义**:攻击线索不丢,记录照写、AI 照样分析,**只是不返回 403**。

> 面试可以直接这么讲:
> "这个请求返回 200 不是我漏了。它的审计记录是 ALERT 不是 PASS ——
> 规则命中了,但这条规则被我故意降级成'只记录不拦',因为它的误报率太高。
> 这是**可量化的取舍**:降级之后正常请求被真正 403 拦掉的比例从 18.8% 降到 4.2%,
> 而攻击拦截一条没少。"

## 四、AI 告警的原文(真实模型输出)

模型是 DeepSeek `deepseek-chat`,通过 OpenAI 兼容接口调用。
下面这些**没有一个字是我写的模板**——是模型自己读审计记录后组织的。

> 但要再强调一次:**这些告警是模型对我们自己发的攻击流量做的判定。**
> 模型是真的、调用是真的、理由是它自己组织的;唯一不真实的是"有攻击者"
> 这件事。见第零节。
>
> 另外,这套数据后来累积到了 6 条告警(多了 MULTI_VECTOR_SCAN 类型),
> 下面列的是最早的三条。

### 告警 #3 — HIGH / 置信度 0.85

> 大量请求命中 SQL-001/003/042 注入规则,且同一 `params_digest`(c694ad…,
> len=20)在数十秒内被高频重复提交,符合自动化 SQL 注入扫描/爆破特征。
> 另有 `/.env` 敏感文件探测(PAT-025)、命令注入(CMD-002)、XSS 及对
> `/api/login`、`/api/register` 等接口的批量 POST 探测,整体呈典型扫描器行为。
> **虽部分请求可能为规则误报,但多规则交叉命中与高频重复模式表明为真实攻击尝试。**

**关联 50 条审计记录。**

### 告警 #2 — HIGH / 置信度 0.85

> 同一 IP 在约 15 分钟内连续发起 8 次被拦截请求,命中 SQL 注入规则
> (SQL-001/003/042/034)、XSS 规则及敏感文件探测(`/.env`,PAT-025),
> 且根路径带相同参数摘要反复触发 SQL 规则,呈现自动化扫描与注入探测特征,
> 非正常业务流量。**虽为拦截状态且部分规则可能误报,但多类型规则集中命中、
> 短时高频、含敏感文件探测,综合判定为真实攻击尝试。**

**关联 8 条审计记录。**

### 告警 #1 — MEDIUM / 置信度 0.60

> 两条记录 URI 均为根路径,但命中 SQL-001/003/042 多条 SQL 注入规则,
> 匹配长度 14 字符,参数摘要相同,说明请求参数中携带了 SQL 注入特征载荷。
> 同一秒内重复出现,符合自动化扫描或注入探测行为。虽未看到原始参数内容,
> 但多规则同时命中且被 403 拦截,判定为真实 SQL 注入尝试的可能性较高,
> 非正常业务字符误报。

## 五、这段输出为什么值得看

对比一下"规则引擎能做到"和"模型做到了"的差别:

| | 规则引擎的输出 | 模型的输出 |
|---|---|---|
| 说了什么 | 命中了 SQL-001、SQL-003、SQL-042 | 这是自动化 SQL 注入扫描,原因有四点 |
| 依据 | 字面量匹配 | 规则类型 + 参数摘要重复度 + 时间密度 + 接口分布 |
| 不确定性 | 无法表达 | 主动说"部分请求可能为误报" |
| 可操作性 | 只能自己去翻日志猜 | 直接给出结论和理由,可人工确认或标误报 |

模型注意到的东西里,**最关键的是 `params_digest` 重复**——这是规则引擎
根本表达不了的判断(规则只看单个请求像不像攻击,不看"同一份载荷被反复提交")。

> 面试可以讲:
> "规则引擎回答'这个请求像不像攻击',模型回答'这一批请求放在一起是什么行为'。
> 前者是单点判断,后者是聚合判断。误报的根源往往是单点判断信息不足,
> 而聚合之后信息就够了吗 —— 这就是为什么这一层不能省。"

## 六、怎么复现

```bash
# 1. 发攻击(9 个请求,约 3 秒)
ssh secguard
cd ~/secguard
./scripts/demo-attack.sh http://127.0.0.1:8088

# 2. 拿管理员令牌
TOKEN=$(curl -s -X POST http://127.0.0.1:8088/api/login \
  -H 'Content-Type: application/json' \
  -d "{\"username\":\"admin\",\"password\":\"$(cat ~/.admin_password)\"}" | jq -r .token)

# 3. 看审计动作分布(BLOCK / ALERT / PASS)
sudo docker exec secguard-mysql mysql -usecguard -p"$(grep '^SECGUARD_DB_PASS=' .env | cut -d= -f2-)" -N -e \
  "SELECT action, COUNT(*) FROM secguard.audit_log
   WHERE created_at > NOW() - INTERVAL 5 MINUTE GROUP BY action;"

# 4. 触发一轮 AI 分析(约 2 秒)
curl -s -X POST -H "Authorization: Bearer $TOKEN" \
  http://127.0.0.1:8088/api/analyze/run | jq

# 5. 看告警
curl -s -H "Authorization: Bearer $TOKEN" \
  "http://127.0.0.1:8088/api/alerts?limit=3" | jq
```

### 注意

- **连跑多轮会累计命中次数**,达到阈值(默认 20 次/5 分钟)会封禁来源 IP。
  本脚本一轮 9 次,两轮还安全。被封了等一会儿,或执行
  `./scripts/demo-attack.sh --reset` 清空计数。
- 从**你自己电脑**打 `http://<服务器IP>:8088`,审计里记的是你的公网 IP;
  在**服务器上**打 `127.0.0.1`,记的是 `172.18.0.1`(docker 网桥)。
  演示时用前者更真实。

> "我发九个攻击请求。八个被当场拦下,一个被记录下来但放行了 ——
