### 想拿到真实流量怎么办

公网服务器被扫描是常态,但现在还没有——原因很简单:

- 服务原来开在 **8088**,通用扫描器主要扫 80/443
- 上线才 8 小时,还没被扫到

**已经做的调整**:`docker-compose.yml` 里给 nginx 加了 `80:80` 映射
(一个容器端口可以映射到多个宿主端口),所以现在 **80 和 8088 同时可用**,
原有链接不受影响。

验证结果:

| 从哪测 | 80 端口 |
|---|---|
| 服务器本机 `curl 127.0.0.1:80` | **200**(正常页面) |
| 另一台公网机器 | **200**(正常页面) |
| 我自己电脑(开着代理) | **502** —— 见下面 |

> **一个坑**:我这台电脑上开着本地代理(`127.0.0.1:7897`),它不转发到
> `<服务器IP>:80` 的请求,返回了一个带 `Proxy-Connection: keep-alive`
> 头的 502。一开始以为是云端拦截了未备案的 80,后来从别的网络位置测才确认
> **服务器本身完全正常**,问题在本地代理。
>
> 判断方法:看响应头。`Proxy-Connection` 不是 nginx 会发的字段 ——
> 一旦看到它,就说明 502 是中间的代理产生的,不是服务器的。
>
> 修法:把服务器 IP 加进代理的绕过列表,或者干脆用 8088 访问。

用 IP 直接访问 80 不需要 ICP 备案(备案是域名解析的要求),所以这条路可行。

### 怎么监控有没有真实攻击进来

配了 `scripts/watch-real-traffic.sh`:

```bash
ssh secguard
cd ~/secguard
./scripts/watch-real-traffic.sh          # 看一次
./scripts/watch-real-traffic.sh --loop    # 每 30 秒刷新
```

它按 IP 汇总审计记录,并把自己人排除掉:

| IP | 是谁 |

| 我的公网 IP | 从本地机器打的验证请求 |

自己人名单存在 `~/.secguard_self_ips`,一行一个 IP。
**家庭宽带的公网 IP 会变**(重启光猫就换),变了之后要往这个文件里加新 IP,

**当前实测(2026-10-26 20:18)**:陌生来源 6 条,其中被判为攻击的 **0 条**。

预期:80 端口开放后,通用扫描器(各种爬虫、botnet、Shodan 类)会在几天内
扫到。典型探测路径是 `/.env`、`/wp-login.php`、`/phpmyadmin`、`/actuator/env`

## 一、这个项目演示什么

一条完整的链路:

```
攻击请求 -> 规则拦截(403) -> 审计落库 -> AI 二次判定(真模型) -> 告警
```

九个请求,八拦一记,然后 AI 从这批记录里读出一个"扫描器行为"的结论。

## 二、演示攻击的输出(原文)

```
$ ./scripts/demo-attack.sh http://127.0.0.1:8088

=== 发送演示攻击(共 8 次)===
  拦截  HTTP 403  /?q=union%20select%201,2,3                   SQL 注入:union select
  拦截  HTTP 403  /?q=1%27%20or%201=1--                        SQL 注入:or 1=1
  放行  HTTP 200  /?q=1%20and%20(select%20count(*)%20from%20user) 子查询(命中 SQL-003,ALERT 级)
  拦截  HTTP 403  /?q=%3Cscript%3Ealert(1)%3C/script%3E        XSS:script 标签
  拦截  HTTP 403  /?q=%3Cimg%20src=x%20onerror=alert(1)%3E     XSS:onerror 事件
  拦截  HTTP 403  /?file=../../../../etc/passwd                路径穿越:/etc/passwd
  拦截  HTTP 403  /?cmd=;cat%20/etc/passwd                      命令注入:cat
  拦截  HTTP 403  /.env                                        敏感文件探测:.env

=== 再补一条请求体攻击(POST body 里的注入)===
  HTTP 403  POST /api/check (body 里带注入)
```

### 那个 200 必须主动解释(否则会被当成漏洞)

它不是漏报。审计表里记着:

```
id     action   status_code   命中规则
1212   ALERT    200           SQL-003
1210   BLOCK    403           SQL-001,SQL-003,SQL-042
```

`SQL-003`(裸 `select ` 关键词)在 `rules/policy.conf` 里被**降级成 ALERT** ——
因为它误伤太多(技术文档、博客正文、SQL 教程里都有 `select`)。

**ALERT 的含义**:攻击线索不丢,记录照写、AI 照样分析,**只是不返回 403**。

> 面试可以直接这么讲:
> "这个请求返回 200 不是我漏了。它的审计记录是 ALERT 不是 PASS ——
> 规则命中了,但这条规则被我故意降级成'只记录不拦',因为它的误报率太高。
> 这是**可量化的取舍**:降级之后正常请求被真正 403 拦掉的比例从 21.2% 降到 3.8%,
> 而攻击拦截一条没少。"

## 四、AI 告警的原文(真实模型输出)

模型是 DeepSeek `deepseek-chat`,通过 OpenAI 兼容接口调用。
下面这些**没有一个字是我写的模板**——是模型自己读审计记录后组织的。

> 但要再强调一次:**这些告警是模型对我们自己发的攻击流量做的判定。**
> 模型是真的、调用是真的、理由是它自己组织的;唯一不真实的是"有攻击者"
> 这件事。见第零节。
>
> 另外,这套数据后来累积到了 6 条告警(多了 MULTI_VECTOR_SCAN 类型),
> 下面列的是最早的三条。

### 告警 #3 — HIGH / 置信度 0.85

> 大量请求命中 SQL-001/003/042 注入规则,且同一 `params_digest`(c694ad…,
> len=20)在数十秒内被高频重复提交,符合自动化 SQL 注入扫描/爆破特征。
> 另有 `/.env` 敏感文件探测(PAT-025)、命令注入(CMD-002)、XSS 及对
> `/api/login`、`/api/register` 等接口的批量 POST 探测,整体呈典型扫描器行为。
> **虽部分请求可能为规则误报,但多规则交叉命中与高频重复模式表明为真实攻击尝试。**

**关联 50 条审计记录。**

### 告警 #2 — HIGH / 置信度 0.85

> 同一 IP 在约 15 分钟内连续发起 8 次被拦截请求,命中 SQL 注入规则
> (SQL-001/003/042/034)、XSS 规则及敏感文件探测(`/.env`,PAT-025),
> 且根路径带相同参数摘要反复触发 SQL 规则,呈现自动化扫描与注入探测特征,
> 非正常业务流量。**虽为拦截状态且部分规则可能误报,但多类型规则集中命中、
> 短时高频、含敏感文件探测,综合判定为真实攻击尝试。**

**关联 8 条审计记录。**

### 告警 #1 — MEDIUM / 置信度 0.60

> 两条记录 URI 均为根路径,但命中 SQL-001/003/042 多条 SQL 注入规则,
> 匹配长度 14 字符,参数摘要相同,说明请求参数中携带了 SQL 注入特征载荷。
> 同一秒内重复出现,符合自动化扫描或注入探测行为。虽未看到原始参数内容,
> 但多规则同时命中且被 403 拦截,判定为真实 SQL 注入尝试的可能性较高,
> 非正常业务字符误报。

## 五、这段输出为什么值得看

对比一下"规则引擎能做到"和"模型做到了"的差别:

| | 规则引擎的输出 | 模型的输出 |
|---|---|---|
| 说了什么 | 命中了 SQL-001、SQL-003、SQL-042 | 这是自动化 SQL 注入扫描,原因有四点 |
| 依据 | 字面量匹配 | 规则类型 + 参数摘要重复度 + 时间密度 + 接口分布 |
| 不确定性 | 无法表达 | 主动说"部分请求可能为误报" |
| 可操作性 | 只能自己去翻日志猜 | 直接给出结论和理由,可人工确认或标误报 |

模型注意到的东西里,**最关键的是 `params_digest` 重复**——这是规则引擎
根本表达不了的判断(规则只看单个请求像不像攻击,不看"同一份载荷被反复提交")。

> 面试可以讲:
> "规则引擎回答'这个请求像不像攻击',模型回答'这一批请求放在一起是什么行为'。
> 前者是单点判断,后者是聚合判断。误报的根源往往是单点判断信息不足,
> 而聚合之后信息就够了吗 —— 这就是为什么这一层不能省。"

## 六、怎么复现

```bash
# 1. 发攻击(9 个请求,约 3 秒)
ssh secguard
cd ~/secguard
./scripts/demo-attack.sh http://127.0.0.1:8088

# 2. 拿管理员令牌
TOKEN=$(curl -s -X POST http://127.0.0.1:8088/api/login \
  -H 'Content-Type: application/json' \
  -d "{\"username\":\"admin\",\"password\":\"$(cat ~/.admin_password)\"}" | jq -r .token)

# 3. 看审计动作分布(BLOCK / ALERT / PASS)
sudo docker exec secguard-mysql mysql -usecguard -p"$(grep '^SECGUARD_DB_PASS=' .env | cut -d= -f2-)" -N -e \
  "SELECT action, COUNT(*) FROM secguard.audit_log
   WHERE created_at > NOW() - INTERVAL 5 MINUTE GROUP BY action;"

# 4. 触发一轮 AI 分析(约 2 秒)
curl -s -X POST -H "Authorization: Bearer $TOKEN" \
  http://127.0.0.1:8088/api/analyze/run | jq

# 5. 看告警
curl -s -H "Authorization: Bearer $TOKEN" \
  "http://127.0.0.1:8088/api/alerts?limit=3" | jq
```

### 注意

- **连跑多轮会累计命中次数**,达到阈值(默认 20 次/5 分钟)会封禁来源 IP。
  本脚本一轮 9 次,两轮还安全。被封了等一会儿,或执行
  `./scripts/demo-attack.sh --reset` 清空计数。
- 从**你自己电脑**打 `http://<服务器IP>:8088`,审计里记的是你的公网 IP;
  在**服务器上**打 `127.0.0.1`,记的是 `172.18.0.1`(docker 网桥)。
  演示时用前者更真实。

## 九、真实攻击复盘(2026-10-27)

第零节写的是首日情况:1,227 条审计,**零真实攻击**。
隔了一天再看,数据完全变了。

### 9.1 一晚上的变化

| 指标 | 10-26(首日 9 小时) | 10-27 |
|---|---|---|
| 审计总量 | 1,227 | **37,000+** |
| 陌生来源 | 6 条 | **34,869 条(96.6%)** |
| 真实攻击 | 0 | **有,而且打了 7.5 小时** |
| AI 告警 | 6 条 | **218 条** |

### 9.2 打我们的是什么

一个**云凭据扫描器**,专门找泄露在 web 目录里的云厂商配置文件。
从它探的路径就能看出来:

| 探测类别 | 次数 | 我们拦住了 |
|---|---|---|
| `.yml` / `.yaml` | 11,214 | 8,504 |
| `.env` 系列 | 8,863 | **8,863(100%)** |
| `.json` | 8,570 | 6,813 |
| 含 secret/key/credential | 881 | 752 |

具体路径全是阿里云那套服务的配置名:
`alibabacloud.yaml`、`actiontrail.config.yaml`、`slb.config.yml`、
`oss.json`、`cs.json`、`acr-config.yml`、`bastionhost.yml`、
`tdsql.config.yaml`、`directmail.json`。

外加 `.env.production`、`.env.local`、`secrets.properties`、
`credentials.properties` 这些通用凭据文件。

### 9.3 头号攻击者

```
69.5.7.147     33,821 次请求     持续 7.5 小时(176 个活跃分钟)
               峰值 ~210 次/分钟
命中 PAT-025(.env 规则)601 次后触发封禁,
然后继续刷了 28,451 次 —— 全被 IP_BANNED 挡住
```

### 9.4 最关键的一个数字

```
敏感路径探测返回 200 的次数:0
```

**零泄漏。** 这是防御有效性的唯一硬指标 —— 不是"拦了多少",
而是"有没有漏出去的"。

### 9.5 这一晚暴露的三个问题(都已修复)

#### 问题 1:规则库对云凭据文件名覆盖不足

`.env` 有规则(PAT-025),但 `alibabacloud.yaml`、`oss.json` 这些全部
返回 **404**。

404 当然也拿不到文件,但区别很大:

| | 403 | 404 |
|---|---|---|
| 审计里的动作 | BLOCK | **PASS** |
| 是否计入封禁计数 | 是 | **否** |
| 攻击者会不会被封 | 会 | **不会** |

所以一个只扫 `.yaml` 的扫描器可以一直扫下去。

**修法**:补了 18 条 `CRED-*` 规则,全部来自当天真实出现过的路径。
其中 3 条较宽的(`config.toml`、`oss.json`、`cs.json`)降成 ALERT ——
技术文档正文里可能提到这些文件名。

#### 问题 2:被封禁后还在逐条写审计(日志放大)

那个被 ban 的 IP 继续刷了 28,451 次,**每次都写一条审计**,
占全库 **79.2%**。而这些记录全是同一句话
(`action=BLOCK`, `rule_hit=IP_BANNED`),没有任何信息量。

**修法**:同一个 IP 在被封期间最多每 60 秒记一条
(`SECGUARD_BAN_AUDIT_INTERVAL`)。请求照样拒绝、照样计入
`requests_blocked`,被压掉的条数记进 `secguard_audit_suppressed_total`
—— **不是悄悄丢**。

实测:56 个请求 → 只写 24 条审计,`suppressed=30` 精确对应,
`requests_blocked=61` 仍然准确。

#### 问题 3:告警疲劳(93.6% 是同一件事)

218 条告警里 **191 条(93.6%)** 是敏感文件探测,来自 **200 个不同 IP**,
每个只打十几下 —— 典型的分布式扫描。

结果是真正高危的 6 条 SQL 注入被彻底淹没。运维看到这个只会做一件事:
**把告警关掉。**

**修法**:一轮内同类型威胁来自 ≥3 个不同 IP 时,合成一条
`ip = multi(N)` 的"分布式扫描"告警,理由里列出所有来源 IP。

实测:2 个来源 IP → 1 条 `multi(2)` 告警。

### 9.6 这次复盘最值钱的地方

**三个问题全是被真实流量打出来的,不是我坐着想的。**

前两周我一直在优化"我觉得该优化的"东西(比如担心引擎匹配速度),
结果真实流量一来,暴露的全是完全没想到的地方:
规则覆盖面的缝隙、日志放大、告警聚合。

> 面试可以这么讲:
> "上线第二天被一个云凭据扫描器打了 3.3 万次。我做的第一件事不是加规则,
> 而是先去查**有没有漏出去的** —— 结果是零。
> 然后我把这一晚的数据当成一次免费的渗透测试复盘:
> 它告诉我规则库缺哪 18 个文件名、封禁后的请求在制造 79% 的日志垃圾、
> 93.6% 的告警是同一件事。这三件事我全都改掉了,并且用同一批数据验证了修法有效。"

### 9.7 修复前后对比

| | 修复前 | 修复后 |
|---|---|---|
| 规则数 | 234 | **252** |
| 凭据探测响应 | 404(PASS,不计数) | **403(BLOCK,计入封禁)** |
| 被封请求的审计 | 每条一行(占 79%) | 每 IP 每分钟最多一行 |
| 2 个 IP 同类探测 | 2 条告警 | **1 条 multi(2) 告警** |

### 9.8 顺带修掉的两个代码 bug

**bug 1:聚合永远不触发**

按 `threat_type` 精确分组,但模型对同一行为给出 `SENSITIVE_FILE_PROBE` /
`SENSITIVE_FILE_PROBING` / `SENSITIVE_FILE_SCANNING` 三种写法 ——
按字符串分组等于把同一件事拆成了三类。

修法:分组前先规范化(取前两段),告警里仍保留模型原始写法。

**bug 2:中文被按字节截断,MySQL 拒收**

`reasoning.substr(0, 200) + "…"` —— 一个汉字占 3 字节,按字节切正好
切在字符中间,留下孤立引导字节,拼上"…"就成了非法 UTF-8:

```
code=1366  Incorrect string value: '\xE9\xE2\x80\xA6' for column 'reasoning'
```

聚合告警写不进库,日志里只有一句"写聚合告警失败",查了很久。

修法:新增 `src/util/utf8.h`,按 UTF-8 边界截断;另外三处同类截断
(模型理由、HTTP 错误片段、审计 URI)一并换掉。

> 这两个 bug 都值得讲 —— 它们不是"没想到",而是
> **"想对了但写错了"**:第一个是字符串比较的粒度问题,
> 第二个是 C++ 里处理文本的经典陷阱。
