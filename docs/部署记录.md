## 三、遇到的五个问题

### 问题 1:22 端口不通,但 sshd 明明在监听

现象:外网连不上 22,控制台 VNC 却能登录。

排查:`sudo ss -ltnp | grep ':22'` 显示 `LISTEN 0.0.0.0:22` —— 服务正常,
那问题就在网络策略层。

根因:这台机器**最初装的是 Windows**(远程桌面走 3389),云防火墙默认规则里
没有 22。重装成 Linux 后规则不会自动补,于是 SSH 被挡在门外。

解决:控制台加 `TCP:22` 和 `TCP:8088` 两条规则。

> 教训:排查要**逐层证明**。先证明服务在听,再证明网络放行,
> 而不是一上来就改 `sshd_config` 重启服务。

### 问题 2:2G 内存编不动这个项目

现象:`docker compose build` 跑到 28% 卡住,日志 6 分钟不动。

排查:`ps` 看到 `cc1plus` 状态 `R`、CPU 87%、**RSS 1.58GB**;
`vmstat` 显示每秒换入 365 页、换出 713 页;可用内存只剩 57MB。

根因:httplib 和 nlohmann/json 都是重模板,单个编译单元峰值 1.5GB 以上。
2 核 2G 机器只能靠 swap 硬撑,陷入换页抖动。加 `-j1` 也救不了,
因为**单个文件就要 1.5GB**。

解决:**本地构建,传镜像**。

```bash
# 本地(20 核,40 秒)
docker compose build app
docker save secguard-app:latest | gzip -1 > /tmp/secguard-image.tar.gz   # 153MB -> 36MB

# 传输(3 秒)
scp /tmp/secguard-image.tar.gz <user>@<host>:/home/<user>/

# 服务器
gunzip -c secguard-image.tar.gz | docker load
docker compose up -d --wait
```

这不是权宜之计,而是 CI/CD 的标准做法:**构建一次,分发产物**。
服务器的职责是运行,不是编译。真要在这台机器上编译,至少需要 4GB 内存。

顺带改了 `docker-compose.yml`:`build.args.BUILD_JOBS` 由
`SECGUARD_BUILD_JOBS` 控制,小内存机器可设 1(提交 4d8c891)。

### 问题 3:github.com 和 Docker 官方仓库不通

现象:`curl https://github.com` 超时,`registry-1.docker.io` 也超时。

解决:
- Docker 本体从**腾讯云镜像源**装:`mirrors.cloud.tencent.com/docker-ce`
- 镜像加速用 `mirror.ccs.tencentyun.com`(腾讯云内网,最快),
  备用 `docker.1panel.live`、`docker.m.daocloud.io`

实测加速器生效:拉 `ubuntu:22.04` 用 **11 秒**。

### 问题 4:自检里"手动触发分析"报 409

现象:自检 1 项失败,`POST /api/analyze/run` 返回 409。

判断:**这是正确行为,不是 bug**。AI 层没启用时,这个接口应该拒绝执行,
而不是假装跑一轮。是我的自检脚本把它当成了失败。

解决:改 `scripts/verify.sh` —— 未启用时期望 409 并算通过;
启用时期望 200。顺带这也成了一条"接口不能一边说没启用一边干活"的检查。

### 问题 5:服务器上没有 wrk,限流测不出来

现象:限流用例跳过。

原因:自检里限流要用并发压测,没有 wrk 时退化成 `xargs + curl`,
并发不够打不空令牌桶。

解决:`apt install wrk`(Ubuntu 22.04 源里有)。装上后限流用例通过
(被限 10765 次)。以后在这台机器上重测性能也用得上。

## 七、怎么让这三个问题不复发

部署完只算"这次成功了"。**让它下次还能成功,需要把坑堵上。**

### 7.1 内存不够:加构建守卫

`docker/deploy.sh` 里加了 `check_build_memory()`:

```bash
如果镜像不存在 && 本机内存 < 3GB
  -> 拒绝构建,打印出"在别的机器构建并传镜像"的完整命令
如果镜像已存在
  -> 直接启动,不再尝试编译
```

这样下次谁在服务器上跑 `./docker/deploy.sh`,不会等二十分钟才发现卡死,
而是立刻看到该怎么做。

### 7.2 镜像被删:本地留一份离线缓存

`docker system prune` 会删掉没在运行的镜像。一旦 `secguard-app` 被删,
`up` 就会尝试重新编译 —— 又卡死。

所以在服务器上留了一份离线缓存:

```
~/.image-cache/                     合计 295MB
  secguard-app_latest.tar.gz         36M
  mysql_8.0.tar.gz                  224M
  redis_7-alpine.tar.gz              16M
  nginx_1.27-alpine.tar.gz           21M
```

配套脚本 `scripts/offline-restore.sh`:

```bash
./scripts/offline-restore.sh --check   # 只检查,列出缺哪些、能不能恢复
./scripts/offline-restore.sh           # 恢复所有缺的镜像(完全不联网)
```

**端到端验证过**:把 `probe/restore:test` 导出 → 删掉 → 用同一句
`gunzip -c ... | docker load` 恢复 → 镜像回来了,线上四个容器全程不受影响。

### 7.3 registry 不通:三重镜像源 + 离线兜底

`/etc/docker/daemon.json` 里配了三个,按顺序尝试:

```
mirror.ccs.tencentyun.com   ← 腾讯云内网,最快(实测拉 ubuntu:22.04 用 11 秒)
docker.1panel.live
docker.m.daocloud.io
```

`docker info` 里确认三行都在 `Registry Mirrors` 下。

真正的兜底是 7.2 的离线缓存:**即使三个加速器全挂,也能从本地 tar 恢复**,
因为服务运行时根本不需要联网,只有拉新镜像才需要。

### 7.4 SSH 加固:改成密钥登录(这件事本来就该做)

上线时 22 端口对全网开着、密码登录开着。**公网 SSH 每天会收到几千次爆破尝试**,
而且初始密码是"生日 + 名字"格式,字典攻击很容易命中。

所以部署完立刻做了加固:

| 项 | 改前 | 改后 |
|---|---|---|
| `PasswordAuthentication` | yes | **no** |
| `PermitRootLogin` | yes | **prohibit-password**(禁止 root 用密码) |
| `MaxAuthTries` | 6 | **3** |

**执行顺序很重要**——先装公钥、验证密钥能登,再关密码:

1. 本地生成密钥:`ssh-keygen -t ed25519`
2. 公钥写进服务器 `~/.ssh/authorized_keys`(权限 600,`~/.ssh` 700)
3. **强制只用公钥测试登录成功**(此时密码还开着,失败也不影响)
4. 备份 `sshd_config` → 改三处 → `sshd -t` 校验语法
5. `systemctl reload ssh`(**不是 restart**,不掐断现有连接)
6. 立刻用密钥再验证一次
7. 验证密码登录已被拒绝

实测结果:

```
maxauthtries 3
permitrootlogin without-password
pubkeyauthentication yes
passwordauthentication no

密钥登录:通过
密码登录:Permission denied(符合预期)
```

本地连接方式(配了别名,不用记参数):

```bash
ssh secguard          # ~/.ssh/config 里配好的
# 等价于
ssh -i ~/.ssh/secguard_ed25519 ubuntu@<服务器IP>
```

> **万一密钥丢了怎么办**:腾讯云控制台的「登录」按钮走 VNC,不经过 SSH,
> 永远能进。进去之后把 `sshd_config.bak.*` 还原、`systemctl reload ssh`
> 就恢复密码登录了。**这就是为什么改配置前必须先备份。**

### 7.5 接入真实大模型(AI 分析层)

上线时 AI 层是关着的(`SECGUARD_AI_ENABLE=0`),因为没有 API Key ——
演示时 `/api/alerts` 是空的,项目最大的亮点看不到。

**先验证服务器能不能访问 API**(当时 github 和 Docker 官方源都不通,
所以这一步必须先做):

```
api.deepseek.com       HTTP 401  耗时 0.16s   ← 通了,401 只是没带 Key
ca-certificates        20260816ubuntu0.22.04.1  ← 证书链正常
```

**改两个变量,重建容器**:

```bash

sed -i 's|^SECGUARD_LLM_KEY=.*|SECGUARD_LLM_KEY=sk-xxx|' .env
sed -i 's|^SECGUARD_AI_ENABLE=.*|SECGUARD_AI_ENABLE=1|' .env

```

其余配置本来就是对的:`SECGUARD_LLM_PROVIDER=openai`(兼容 OpenAI 接口)、
`SECGUARD_LLM_BASE_URL=https://api.deepseek.com/v1`、`SECGUARD_LLM_MODEL=deepseek-chat`。

**实测结果(真实调用,不是 mock)**:

```
provider openai   model deepseek-chat   llm_available true
calls 3   ok_calls 3   transport_errors 0   parse_errors 0   llm_retries 0
单轮耗时 1945 ms(一次 LLM 调用)
```

模型输出的告警理由样例:

> 大量请求命中 SQL-001/003/042 注入规则,且同一 params_digest 在数十秒内被
> 高频重复提交,符合自动化 SQL 注入扫描/爆破特征。另有 /.env 敏感文件探测
> (PAT-025)、命令注入(CMD-002)、XSS 及对 /api/login、/api/register 等接口的
> 批量 POST 探测,整体呈典型扫描器行为。虽部分请求可能为规则误报,
> 但多规则交叉命中与高频重复模式表明为真实攻击尝试。

它做的不只是"命中规则就算攻击",而是交叉比对了:规则类型、参数摘要重复度、
时间密度、被探测的接口分布,并且主动说明了不确定性。

**成本控制**(配置里本来就有,不需要额外做):

| 参数 | 值 | 作用 |
|---|---|---|
| `SECGUARD_AI_RPM` | 10 | 每分钟最多调 10 次,硬上限 |
| `SECGUARD_AI_BATCH` | 10 | 每轮最多分析 10 条记录 |
| `SECGUARD_AI_INTERVAL` | 120s | 每 2 分钟跑一轮 |
| `SECGUARD_AI_MIN_CONFIDENCE` | 0.6 | 低于此值不写告警 |

只分析**被拦截**的记录,所以量天然就小。按上面的上限,即使整天被攻击,
一小时最多 600 次调用、每次约 700-1000 token。

### 7.6 数据库备份

上线后数据库里攒了 3.6 万条审计、221 条告警、若干用户。服务器一出问题
或者试用到期忘了续费,这些全都没了。所以配了自动备份。

**`scripts/backup-db.sh`**,四个子命令:

| 命令 | 作用 |
|---|---|
| 无参数 | 备份一次 |
| `--list` | 看已有备份 |
| `--verify <文件>` | 校验某个备份的完整性 |
| `--restore-test` | 把最新备份**真的恢复**到一个临时库,逐表比对行数 |

**定时任务**(`crontab -l`):

```
30 3 * * *  backup-db.sh                       每天 03:30 备份
0 4 * * 0   backup-db.sh --restore-test        每周日 04:00 恢复测试
```

**几个设计取舍**:

- **用 root 而不是应用账号**:`mysqldump` 需要 `LOCK TABLES` / `PROCESS` 之类
  的额外权限,应用账号只有 DML,直接失败。
- **`--single-transaction`**:InnoDB 下走一致性快照,不锁表。所以备份可以
  在任何时间跑,不用挑凌晨(定 03:30 只是因为流量低)。
- **备份完立刻 `gzip -t` 校验 + 检查含 `CREATE TABLE`**:一个损坏的备份
  比没有备份更危险 —— 你以为有。
- **备份目录 700 / 文件 600**:里面是全库数据,含用户口令哈希。
- **保留 7 天**(`KEEP_DAYS`)。

**实测恢复结果**(2026-10-27):

```
user       生产 3      恢复 3      一致
post       生产 2      恢复 2      一致
comment    生产 0      恢复 0      一致
audit_log  生产 36244  恢复 36244  一致
alert      生产 221    恢复 221    一致

恢复测试通过:5 张表全部对得上
```

备份体积 806 KB(压缩后),目前 3 份共 2.4 MB,磁盘剩 29 GB。

**已知局限(必须说清)**:备份和数据库在同一块磁盘上。磁盘坏了、机器被释放,
备份跟着一起没。要真正抗灾,得把备份推到另一台机器或对象存储 —— 现在没做。

#### 写这个脚本踩到的两个坑(都很安静)

**坑 1:`grep -q` + `pipefail` + SIGPIPE**

```bash
if ! zcat "$tmp" | grep -q 'CREATE TABLE'; then   # 看起来没问题
    rm -f "$tmp"                                   # 但好备份被删了
fi
```

`grep -q` 一匹配到就立刻退出 → `zcat` 收到 SIGPIPE 非零退出 →
脚本开了 `set -o pipefail`,整个管道变成非零 → `if !` 判定为失败。

结果:825 KB 的正常备份被当成"空库"删了两次。

修法:用 `grep -c`(读完全部输入,不提前退出)代替。

**坑 2:`docker exec` 不加 `-i` 会关掉标准输入**

```bash
zcat backup.sql.gz | docker exec mysql ...   # SQL 根本没进去
```

不加 `-i` 时 docker 立即关闭 stdin,管道里的数据全丢,**而且退出码是 0**。
表现为"恢复成功,但临时库里一张表都没有"。

修法:专门加一个 `myexec_i()` 带 `-i`,并且不依赖退出码判断成败 ——
改成直接数临时库里有几张表。**事实比退出码可靠。**

> 这两个坑都值得讲:它们的共同点是**不报错**。第一个把好数据删了,
> 第二个让恢复静默失败。如果没有"真的恢复一次并比对行数"这一步,
> 这套备份会一直显示正常,直到真出事的那天才发现它是空的。

### 7.7 还没根治的部分(说清楚)

| 问题 | 状态 | 为什么不能根治 |
|---|---|---|

**要不要为编译加内存?** 不需要。镜像构建本来就该在 CI 或开发机上做,
服务器只负责运行 —— 现在这套流程和标准 CI/CD 是一致的,加内存只是浪费钱。
