# 数据持久化专项审查

> 2026-11-04 做的一次针对性审查。范围是**数据从产生到落库、到备份、到清理**的
> 整条链路,因为这条链路出问题不会报错,只会在某天发现"数据对不上"。
>
> 结论:**找到 5 个问题,其中 2 个是"功能写了但没生效"级别的**。
> 全部已修复并实测验证。

---

## 一、审查范围与方法

| 环节 | 文件 | 看什么 |
|---|---|---|
| 审计入队 | `src/net/http_server.cpp` (`record_audit`) | 有没有路径静默不记 |
| 异步管道 | `src/db/audit_writer.cpp` | 队列满/失败/停机的数据去向 |
| 批量落库 | `src/db/dao.cpp` (`write_audit_batch`) | 事务、分块、失败回滚 |
| 连接池 | `src/db/connection_pool.cpp` | 借还、异常时是否泄漏 |
| 分析回写 | `src/ai/analyzer.cpp` | `analyzed` 标记时机 |
| 数据清理 | `main.cpp` + `dao.cpp` (`purge_audit_before`) | 索引、批量、影响 |
| 备份 | `scripts/backup-db.sh` | 是否全表、能否恢复 |
| 表结构 | `db/schema.sql` | 索引、列宽、类型 |

方法:**读代码找疑点,然后在线上用可逆的方式造故障验证**。
不满足于"代码看起来对",要看到"故障发生时数据确实还在"。

## 二、发现的问题

### 🔴 问题 1:ALERT 级记录从来没进过 AI 分析(功能失效)

**这是最重要的一条。**

`alert` 这个分层(把宽规则降级成"记录但不拦")的设计目的是:
**让可疑但不确定的行为继续被看见,并且交给 AI 判断真假。**
文档里也是这么写的:"仍然记录、仍然进 AI 分析"。

但实际查询结果:

```
action    total   analyzed_yes   analyzed_no
ALERT       187        0             187     ← 一条都没被分析过
BLOCK      1525      693             832
PASS       3015        0            3015
```

**根因**:判断"要不要分析"这件事,在**三个地方各写了一套**:

| 位置 | 判断条件 |
|---|---|
| `dao.cpp` `fetch_unanalyzed` 的 SQL | `analyzed=0 AND action='BLOCK' AND rule_hit NOT IN (策略性拦截)` |
| `analyzer.cpp` `is_analyzable()` | 只看 `rule_hit`,不看 `action` |
| 写库时 `analyzed` 字段 | 硬编码 `0` |

SQL 里的 `action='BLOCK'` 把 ALERT 全排除了。而为了"让宽规则也能被看见"
才加的规则,恰好全是 ALERT 级:

| 规则 | 命中次数 | 有没有产生过告警 |
|---|---|---|
| `PAT-037`(phpmyadmin) | 79 | ❌ |
| `PAT-036`(phpinfo) | 21 | ❌ |
| `SQL-058` | 19 | ❌ |
| `PAT-039`(info.php) | 15 | ❌ |
| `PAT-038`(claude.md) | 11 | ❌ |
| `CRED-017` / `CRED-030` / `CRED-029` | 9 / 9 / 8 | ❌ |

**所以那个 phpMyAdmin 扫描器(128 次、0 拦截)虽然"被记录"了,
但一次 AI 判断都没触发 —— ALERT 分层等于半个死胡同。**

**修法**:

1. 把判断收敛到一个地方:`src/db/analyze_policy.h`
   ```cpp
   inline bool needs_llm_analysis(const std::string& action, const std::string& rule_hit) {
       if (action != "BLOCK" && action != "ALERT") return false;  // ← ALERT 也算
       if (rule_hit.empty()) return false;
       return !is_policy_hit(rule_hit);
   }
   ```
2. SQL 改成 `action IN ('BLOCK','ALERT')`
3. `analyzer.cpp` 的 `is_analyzable` 改为调用同一个函数,不再各写一套

**修复后实测**:ALERT 的 `analyzed_yes` 从 **0 → 16**,
并且产生了新告警 —— 其中一条是:

```
id=615  ip=multi(3)  threat_type=RECONNAISSANCE
```

**AI 认出了那批路径探测是"侦查行为"**,而这是修复前完全看不到的。

### 🔴 问题 2:告警写库失败时,记录仍被标记"已分析" → 告警永久丢失

`insert_alert` 失败后的处理有一行 `continue`,注释写着
"写失败就不标记,下轮再试"。但这是**没有聚合功能的版本**的写法。

我后来加告警聚合时,把"标记已分析"的时机从循环内挪到了循环后的统一处理:

```cpp
// 循环里:无条件收集所有 id
for (const auto& r : group) analyzed_ids.push_back(r.id);

// 循环后:统一标记
if (!dao_->mark_analyzed(analyzed_ids)) { ... }
```

于是**即使告警写库失败,那批记录还是被标记成已分析** → 下一轮不会再取到
它们 → 告警永久丢失,**而日志里只有一句"写告警失败"**。

**这个 bug 在线上真的发生过一次**:10-27 的 UTF-8 截断导致 MySQL 返回
`code=1366`,`写聚合告警失败 类型=SENSITIVE_FILE` —— 那 2 个 IP 的记录
被标记了,对应的告警再也没生成。

**修法**:每条候选告警带上它的来源记录 id,只有**落库成功**才把这些 id
放进 `analyzed_ids`:

```cpp
struct Pending {
    AlertRow row;
    std::string ip;
    std::vector<std::int64_t> source_ids;   // 新增
};
// 成功:for (auto id : pending[i].source_ids) analyzed_ids.push_back(id);
// 失败:不添加,日志写明"这 N 条记录保留待下轮重试"
```

**验证方式(可逆地注入故障)**:

用触发器让 `alert` 的插入必然失败:

```sql
CREATE TRIGGER t_force_fail BEFORE INSERT ON alert FOR EACH ROW
SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'simulated failure';
```

实测结果:

| 步骤 | 待分析记录 | 告警数 |
|---|---|---|
| 触发器生效,跑一轮分析 | 15 → **15**(未被标记) | 611 → 611 |
| 日志 | `写告警失败 ip=...,这 3 条记录保留待下轮重试` | |
| 删掉触发器,再跑一轮 | 15 → **12**(被标记) | 611 → **612** |

### 🟡 问题 3:停机时入队的记录被静默丢弃,不计数

```cpp
void AuditWriter::submit(const AuditLogRow& row) {
    if (!running_.load()) return;   // ← 直接返回,dropped_ 不增加
    ...
}
```

停机流程中 `running_` 先变 false,但此时还可能有权在处理的请求走到
`record_audit`。这些记录写不进去是必然的,但**必须计数** ——
否则事后无法解释"审计数比请求数少了几条"。

**修法**:这条路径也 `dropped_.fetch_add(1)`。

### 🟡 问题 4:保留策略的 DELETE 是全表扫描

```sql
DELETE FROM audit_log WHERE created_at < (NOW() - INTERVAL 30 DAY) LIMIT 10000
```

`EXPLAIN` 结果:`type=ALL, rows=4841` —— **没有任何索引**,每次清理都全表扫。
这个语句**每 10 分钟跑一次**。

表小的时候无所谓,但审计表正是那种会慢慢变大的表
(历史峰值:压测时 320 万行)。

**修法**:`audit_log` 加 `KEY idx_created (created_at)`,并在 `schema.sql`
里同步(注意别和 `post` 表已有的 `idx_created_at` 搞混)。

**修复后**:

```
type=range  key=idx_created  rows=1
```

### 🟡 问题 5:`analyzed=0` 里堆了 3,848 条永远不会被分析的记录

写库时 `analyzed` 硬编码为 0,所以:

- **PASS 记录**(3,015 条):SQL 要求 `action='BLOCK'`,永远不会被取
- **策略性拦截**(IP_BANNED / RATE_LIMITED 等):SQL 明确排除

这些记录永远停在 `analyzed=0`,白占 `idx_analyzed` 索引,
而且分析器每一轮都要把它们捞出来再过滤掉一遍。

**修法**:写入时就按"要不要分析"定好 `analyzed`(使用问题 1 里的
`needs_llm_analysis`),并对历史数据回填:

```
回填前 analyzed=0: 4,025
回填后 analyzed=0:   177     ← 清掉 3,848 条垃圾
```

回填后待分析队列里只剩 `ALERT 177` —— **正好是问题 1 里从来没被分析过的那批**,
修完之后它们开始被处理了。

## 三、确认没问题的部分(审查也要有结论,不能只报问题)

| 检查项 | 结论 |
|---|---|
| **写库事务性** | `write_audit_batch` 关自动提交 → 分块(50 行/批)多行 INSERT → 统一 commit;异常时 rollback 并恢复 autocommit ✓ |
| **停机顺序** | 先 `svr.stop()` → join 三个后台线程 → **最后** `audit->stop()` 排空队列 → 再查统计 → 连接池最后析构。顺序正确,写线程不会用到已销毁的连接池 ✓ |
| **队列容量与背压** | 16,384 条环形队列;满了丢弃并计数(fail-open,不让审计拖垮主链路)✓ |
| **批量重试** | 落库失败重试 3 次(50/100/150ms 退避),仍失败则丢弃并计数 ✓ |
| **列宽与截断一致** | `uri` 截 500 / 列 512;`params_digest` 1000 / 1024;`rule_hit` 120 / 128;`method` 15 / 16 —— 都留了余量 ✓ |
| **UTF-8 截断** | 已统一走 `utf8::truncate`(见部署记录 7.x 的 1366 错误)✓ |
| **备份完整性** | 备份里 5 张表齐全(`alert`/`audit_log`/`comment`/`post`/`user`),与线上一致;恢复测试逐表比对行数通过 ✓ |
| **同步兜底路径** | 审计管道未启用时走同步写,失败会打 warning ✓ |
| **告警 log_ids** | 上限 1000 字符 / 列 1024,合并时也做了截断 ✓ |

## 四、遗留的两个已知问题(不改,但要说清)

### 1. 告警的 `log_ids` 可能指向已被清理的审计记录

保留策略删掉的审计行,`alert.log_ids` 里还留着它们的 id。
点开告警想追溯原始日志时,可能查不到。

**为什么接受**:告警本身是结论,审计是过程。审计有保留期是合理的;
真要长期追溯,应该把告警相关的审计单独归档(现在没做)。

### 2. 自检的"AI 分析层"那一组偶发跳过

`verify.sh` 第 9 组依赖"队列里有待分析记录",如果刚跑过一轮分析把队列清空,
这一组会显示"跳过"。实测出现过一次 `53 通过 / 0 失败 / 1 跳过`。

**为什么暂时不改**:它只是偶发显示问题,不影响功能;正确做法是
这一组自己先造一条命中规则的记录再验证,属于自检脚本的打磨。

## 五、这次审查的方法论(可以拿去讲)

1. **先读代码找疑点,再去线上用可逆方式造故障。**
   问题 2 如果只读代码,很容易得出"有 continue 所以没问题"的错误结论 ——
   那个 `continue` 属于旧版本。只有真的让插入失败一次,才看得出记录被误标了。

2. **"写到文档里的功能"和"代码里生效的功能"要对账。**
   问题 1 就是这么发现的:文档说 ALERT 也进 AI,查一下 `analyzed_yes` 全是 0,
   立刻暴露。**任何"应该发生"的事,都要有一个可以直接查的指标。**

3. **默认值要跟着场景走。**
   保留 7 天是压测时代的取值,线上长期运行时它把最有价值的证据删了
   (见部署记录 7.9)。

4. **同一个判断不要写三遍。**
   问题 1 和问题 5 的根因都是"要不要分析"这件事散落在 SQL、C++、写库三处。
   收敛到 `analyze_policy.h` 之后,这类"某一处漏了"的问题从结构上消失。
