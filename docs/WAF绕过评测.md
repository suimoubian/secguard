# WAF 绕过评测与归一化检测层(项目 A)

> 完成于 2026-10-25。数据由 `tools/waf_eval` 现场跑出,可用
> `./scripts/eval-waf.sh` 复现,机器可读版本在 [评测数据/最新.md](评测数据/最新.md)。

---

## 零、一句话

我给自己的 WAF 建了一套**可复现的绕过评测**:82 条"同一攻击的不同写法"里,
原引擎漏掉 **50 条(61.0%)**;加一层归一化(编码还原 + 注释折叠 + 空白压缩)后
降到 **5 条(6.1%)**,代价是误报 **+2.1 个百分点**、每条请求检测耗时
**+0.37 µs**。

再把"看见"和"拦下"拆成两层(策略文件,第十节):5 条宽规则降成 ALERT 后,
正常样本里**被真正 403 拦掉**的比例从 **18.8% 降到 4.2%**,而攻击的拦截一条没少。

## 一、问题是怎么发现的

不是"猜"出来的,是读代码读出来的。`src/net/app_context.cpp` 里把 HTTP
翻译成待检文本时,注释写得明明白白:

```cpp
append_segment("QUERY:", query);          // 原样,不解码
append_segment("BODY:",  body);           // 原样,不解码
```

而 `Engine::search` 里只做了一次 `to_lower`。所以检测看到的是**未解码的原始
字节**。后果:

```
?q=1 union select 1        -> 命中 SQL-001
?q=1%20union%20select%201  -> 什么也命中不了
```

后一种写法不是"高级绕过手法",它是浏览器和 `curl --data-urlencode` 的默认行为。
而已有的 228 条规则里,有相当一部分含空格(`union select`、`or 1=1`、
`order by 1--`),在 URL 编码面前直接失效。

**为什么 `verify.sh` 54 项全过也没发现**:自检用的是明文请求,
`curl "http://host/?id=1 union select 1"` 会把空格原样发出去。
测试和真实流量之间差了一个"编码"。这本身就是一条值得讲的教训:
**测试通过不等于防线有效,得看测试用了什么形态的输入。**

## 二、评测方法(先有尺子,再谈改不改)

### 2.1 语料不是"一堆攻击载荷",而是"基线 + 变形的对照"

一条 payload 漏了,可能因为它本来就不该被检出。为了让"漏报"这个词有意义,
每条变形样本都必须能追溯到一个**基线样本**,而基线样本必须是**原引擎确实能拦住**
的明文写法:

```
sqli-b01  baseline  id=1' or 1=1--            (无来源,原引擎命中)
sqli-v01  percent-space  id=1'%20or%201=1--   (来源 = sqli-b01)
```

评测时只统计"基线命中、变形漏掉"的样本 —— 这种才叫**被绕过**。
这个约束是整个方法论的支点,没有它,漏报率就是一个可以随手刷大的数字。

### 2.2 语料规模与构成

| 组 | 条数 | 作用 |
|---|---|---|
| 基线样本 | 39 | 证明原引擎确实能检出(实测 39/39 全中,100%) |
| 变形样本 | 82 | 测"同一攻击换写法"之后还剩多少检出 |
| 正常样本 | 48 | 误报的分母 |

覆盖 4 类攻击(SQL 注入 / XSS / 命令注入 / 路径穿越)× 37 种手法
(百分号编码、双层编码、部分编码、注释、版本注释、HTML 实体、JS 转义、
NUL、空白变形、等价语法……)。

### 2.3 三个指标的定义

| 指标 | 定义 | 为什么这样定义 |
|---|---|---|
| 基线检出率 | 基线样本中被检出的比例 | 它必须接近 100%,否则说明语料本身有问题 |
| 变形漏报率 | **基线命中**的变形样本中,漏掉的比例 | 分母是"本来能拦住的",这才是绕过的严格定义 |
| 误报率 | 正常样本中被判黑的比例 | 只看检出率会让"全部拦截"这种蠢方案拿满分 |

### 2.4 一个容易踩的坑:特征污染

最初写 XSS 语料时,变形样本里都带着 `alert(1)`。结果基线靠 `alert(` 这条规则
把 22 条变形全部兜住了 —— 我测的根本不是标签规则。

改法:**每条基线只允许被一个特征命中**,变形样本也不能顺带带上别的特征。
于是基线改成 `q=<script>`、`q=<img src=x>`、`q=javascript:1` 这种"只有一个
检测点"的形态。这一步之后真实数字才浮出来(基线漏报从 46% 涨到 61%)。

**教训:评测语料本身会骗人,而且骗得比攻击者还悄无声息。**

## 三、基线:61.0% 的变形被绕过

| 类别 | 有效变形 | 基线漏报 | 漏报率 |
|---|---|---|---|
| SQL 注入 | 34 | 18 | 52.9% |
| XSS | 22 | 18 | 81.8% |
| 命令注入 | 15 | 9 | 60.0% |
| 路径穿越 | 11 | 5 | 45.5% |
| **合计** | **82** | **50** | **61.0%** |

按手法看,漏报最集中的三类:

| 手法 | 变形数 | 基线漏报 | 根因 |
|---|---|---|---|
| percent-space / plus-space / tabular-space / newline-space | 15 | 10 | 空白被编码,含空格的特征全部失效 |
| separator-encode | 7 | 6 | `;` `|` `$` `(` 等分隔符被编码 |
| double-encode / partial-percent-encode / keyword-percent-encode | 13 | 11 | 编码层数与位置任意组合 |

XSS 漏报 81.8% 最严重,原因是它的特征几乎全是标签字面量(`<script`、`<img`),
标签名里任意一个字符被编码就整体失效。

## 四、归一化层:只做"还原",不做"猜测"

### 4.1 处理流水线

```
原始文本
  ├─ 1. percent-decode   %20 / %3C,循环解到不再变化(上限 3 层,应对双层/三层)
  ├─ 2. escape-decode    \x3c / \u003c / \u{3c} / \/
  ├─ 3. entity-decode    &#x6a; / &#106; / &lt; / &Tab;
  ├─ 4. NUL 剔除         %00 —— 很多解析器在 \0 处截断,`..%00/` 等价于 `../`
  ├─ 5. block-comment    /**/ 折叠成空格;/*!50000x*/ 保留 x、丢掉外壳
  ├─ 6. whitespace       任意空白串压缩成一个空格,并去掉首尾
  └─ 7. lowercase       规则库是小写的
       ↓
     规范形 → 再跑一遍自动机 → 与第一遍的命中取并集
```

### 4.2 为什么是"两遍取并集"而不是"替换掉第一遍"

```cpp
// src/engine/engine.cpp
scan_into(normalize(text), ...);                 // 第 1 遍:原样,行为与改造前完全一致
if (may_obfuscate(text)) {
    scan_into(canonicalize(text), ...);          // 第 2 遍:规范形
}
sort + unique                                     // 并集
```

第 1 遍一个字没动,所以**已有检出能力零回归**;第 2 遍只会增加命中。
安全组件的"升级"如果可能降低既有检出率,那升级本身就是事故。

关闭开关:`SECGUARD_ENGINE_NORMALIZE=0`,退回原行为(用于线上止损和消融实验)。

### 4.3 顺序为什么不能换

- 编码必须最先解:先做实体解码的话,`%26%23x3c%3b`(即 `&#x3c;`)根本看不到 `&`;
- 注释必须在空白折叠之前:折叠会把 `/*\n*/` 里的换行变成空格,导致 `/*` 和 `*/`
  仍然匹配得上,但 `/*!50000` 的版本号解析会错位;
- NUL 剔除必须在空白折叠之前:`..%00/` 要变成 `../`,而不是 `.. /`。

### 4.4 两个"设计做错了"的记录(比做对的部分更值钱)

**错误一:顺手把 `--` 行注释也剥了。**

看起来很合理 —— SQL 里 `--` 就是注释。但规则库里有 `order by 1--`、`or true--`、
`'--` 这种**把注释一起写进特征本体的规则**。归一化把 `--` 到行尾删掉之后,
这些规则在规范形里永远命中不了。

实测表现很隐蔽:编码空格的 `order by 1--` 在加固后**仍然漏报**,而其他变形都修好了。
排查结论:**归一化只能做"还原",不能做"删除信息"**。行注释是证据,不是噪音,保留。

**错误二:第二遍无条件执行,性能白付。**

第一版用 `canonical != normalized` 判断要不要跑第二遍。但 `build_scan_text`
用 `\n` 分隔 PATH/QUERY/BODY/UA 四段,而空白折叠会把 `\n` 变成空格,
于是**每条请求的规范形都和原文不同**,判断恒为真,第二遍永远执行。

修法:加一个带早退的 `may_obfuscate()` 预扫描(找 `%`、`+`、`\`、`\t`、
`/*`、连续空格、`&` 后跟 `#`/`名字;`)。实测 169 条样本里只有 95 条需要第二遍,
其余 74 条直接走快路。

### 4.5 归一化 + 规则是配套的,不能只做一半

归一化之后还漏的 5 条里,有 2 条是 `java\nscript:` / `java\tscript:`。
折叠之后它们都变成 `java script:`,于是**一条规则覆盖整个变形族**:

```
java script:    NORM-001  XSS  HIGH
vb script:      NORM-002  XSS  HIGH
```

这就是归一化的真正价值:它把**无穷多种写法**收敛成**有限几种形状**,
规则才可能写得完。只加规则不归一化,就得为每种编码各写一条,永远追不上。

## 五、加固后的结果

| 指标 | 基线 | 加固 | 变化 |
|---|---|---|---|
| 基线样本检出率(39) | 100.0% | 100.0% | ±0 |
| **变形漏报率(82)** | **61.0%** | **6.1%** | **-54.9 pp** |
| 正常样本误报率(48) | 16.7% | 18.8% | +2.1 pp |
| 每样本检测耗时 | 0.258 µs | 0.628 µs | +0.37 µs |

按类别:

| 类别 | 基线漏报 | 加固漏报 |
|---|---|---|
| SQL 注入 | 18 / 34 | **1** / 34 |
| XSS | 18 / 22 | **2** / 22 |
| 命令注入 | 9 / 15 | **2** / 15 |
| 路径穿越 | 5 / 11 | **0** / 11 |

### 5.1 引擎级:能分辨出来,但绝对值很小

+0.37 µs/请求。单看倍数是 2.43x(看着吓人),按 3.6 万 QPS 折算,
单核占用增加约 **1.4%**。检测本身在微秒级,真正花时间的是 HTTP 解析和数据库,
所以这里**绝对值的意义大于倍数**。

### 5.2 端到端:功能上确实生效

压测容器直连 app(绕开 nginx),同一个编码载荷,只切 `SECGUARD_ENGINE_NORMALIZE`:

| 载荷 | 归一化关 | 归一化开 |
|---|---|---|
| SQL 注入(空格编码 `%20`) | 200 | **403** |
| XSS(标签名部分编码 `%3Cscr%69pt%3E`) | 200 | **403** |
| 路径穿越(反斜杠编码 `%2e%2e%5c`) | 200 | **403** |
| XSS(scheme 内插换行 `java%0Ascript:`) | 200 | **403** |

这一张表比所有微基准都重要:**同一个请求,改一个环境变量,从放行变成拦截。**

线上那套(经 nginx,`:8088`)也复测过同样的四个载荷:全部 403,
正常请求(含 `%E4%B8%AD...` 这种中文编码)仍是 200,`/health` 200。

### 5.3 端到端吞吐:分辨不出来(而这是好事)

2 核 / 64 连接 / 8 秒 / 5 轮交错测量(每轮"关/开"交替,避免机器性能漂移被
算进配置差异):

| 工作负载 | 归一化关 QPS | 归一化开 QPS | 变化 | 关 P99 | 开 P99 |
|---|---|---|---|---|---|
| 无变形标记(对照组) | 2983 | 3054 | **+2.4%** | 83.8 ms | 76.6 ms |
| 带 `%XX` 编码(第二遍执行) | 3079 | 3037 | **−1.4%** | 75.3 ms | 77.1 ms |

**怎么读**:对照组走快路,两种配置执行的代码完全相同,所以它那一行的
±2.4% 就是**这台机器的噪声水平**。编码组是 −1.4%,符号和对照组相反、
幅度还更小 —— 结论是**端到端测不出归一化层的成本**。

算一下就明白了:2 核跑到约 3000 QPS,单请求平均占用约 660 µs CPU;
而检测只有 0.6 µs,占 **0.09%**。用端到端指标去分辨 0.09%,
超出这台机器的测量能力。

(绝对值明显低于 [性能数据.md](性能数据.md) 里的 3.6 万 QPS,原因是
这轮 app 跑在 docker 里、MySQL/Redis 在另一个容器走网桥,和本机原生跑
不是一回事。**两套数字不能互相比较**,这里只用来做 A/B。)

### 5.4 这条结论本身值得讲

"引擎级 +168%、端到端 0%"看着矛盾,其实说明了一件正经事:
**性能数字必须说清楚是在哪一层测的**。同一个改动在两层差两个数量级,
拿哪个数写简历,取决于你想让人看什么 —— 而我两个都写,因为
面试官如果追问"线上到底有没有影响",答案只能是端到端的那一个。

**误报代价**:9 条误报里只有 1 条是新引入的(`%3Cinput` 解码后命中 `<input`),
其余 8 条是原有规则过宽的存量问题 —— 明细见下一节。

## 六、残差:5 条修不动的,以及为什么

| 样本 | 手法 | 为什么归一化救不了 |
|---|---|---|
| `id=1' or 2>1--` | 等价语法 | 语义上等价于 `or 1=1`,但字面完全不同,子串匹配没有推理能力 |
| `and sleep (5)` | 函数名与括号间加空格 | `sleep (` 与 `sleep(` 是两个字符串;能补规则,但每换一个函数就得补一条 |
| `top['al'+'ert'](1)` | JS 字符串拼接 | `alert` 被拆成两段,只有做 JS 解析(AST)才能还原 |
| `echo Y3JhdA== \| base64 -d \| sh` | base64 载荷 | 检测层不做解码执行,天然看不见 |
| `; w\hoami` | 反斜杠转义 | shell 把 `\h` 当 `h`,但这是"执行语义",不是"编码语义" |

**结论**:子串 + 归一化能覆盖**编码类、分隔符类、注释类**的绕过,
覆盖不了**语法等价**和**跨字符拆分**。后者要靠 AST/语义分析,
那是下一代检测引擎的活 —— 这也正好说明工业界为什么从"规则匹配"走向
"语义分析"(雷池/SafeLine 就是这条路)。

知道边界在哪,比声称"没有边界"值钱。

## 七、顺带发现的三个规则库缺陷

评测过程中,`--dump-rules` 把"引擎实际加载的规则"打出来对账,发现了三个
静默问题(都不报错,只是行为不是作者想要的那样):

### 7.1 以 `#` 开头的规则永远不会被加载

```text
规则文件第 42 行:  #	SQL-033	SQL_INJECTION	MEDIUM
```

加载器把 `#` 开头的行当注释跳过,所以这条规则**从来没生效过**。
它本该检出"单独的井号"(SQL 注释符),实际一直是死规则。

### 7.2 尾空格被 `trim` 掉,语义变了

规则文件里写的是 `select `(带尾空格,本意是"select 后面跟空格"),
但加载时每个字段都 `trim`:

```
规则文件:  select <TAB> SQL-003 ...
引擎加载:  select
```

于是它变成"只要出现 select 五个字母就拦"。后果有两面:
- 好处(意外的):编码空格的 `union%20select` 也能被它兜住,基线漏报率被低估了;
- 坏处:`select * from users`(技术文档、博客正文)全部误报 —— 实测 3 条。

### 7.3 超宽规则贡献了全部存量误报

9 条误报的归因:`SQL-003`(select)×3、`SQL-058`(0x)×1、`SQL-001`(union select)×1、
`PAT-034`(/home/)×1、`PAT-035`(/var/www)×1、`PAT-001`(../)×1、`XSS-007`(<input)×1。

这条线索指向的不是"再改归一化",而是**处置策略**:这些规则不是不该有,
是不该"命中就 403"。见第十节。

## 十、规则分级:把"看见"和"拦下"分开

### 10.1 为什么不能靠删规则降误报

上面 8 条误报来自 6 条超宽规则。直接删掉它们,误报是降了,但这些线索也没了:
`select`、`0x`、`../` 出现在流量里**本身是有价值的信息**,只是不该单独构成
"拦截"的理由。

所以把两层拆开:

| 层 | 回答什么问题 | 放哪 |
|---|---|---|
| 规则库 | 这条流量**像不像**攻击 | `rules/attack_patterns.txt` |
| 处置策略 | 像到什么程度才**值得拦** | `rules/policy.conf` |

```
default BLOCK
SQL-003 ALERT    # 出现 select 五个字母就拦 -> 改成只记 ALERT
SQL-058 ALERT    # 0x 十六进制前缀
PAT-034 ALERT    # /home/
PAT-035 ALERT    # /var/www
XSS-007 ALERT    # <input>
```

判定口径:**一个请求的命中里只要有一条 BLOCK 级规则,就拦**;全是 ALERT 级
则放行,但审计里写 `action=ALERT`。取最严是为了避免"一条宽规则被降级,
把同一请求里更严重的命中也放过"。

### 10.2 关键取舍:ALERT 不计入封禁计数

如果 ALERT 也计入 `record_hit`,一篇提到 `select` 的技术博客,作者点几次
就把自己 IP 封了 —— 那正是这些规则被降级的原因,不能一边降级一边保留它的副作用。

代价要说清楚:**只触发 ALERT 的攻击不会累积封禁**。所以只降"宽而不准"的规则,
精确规则(`<script>`、`/etc/passwd`、`; cat`)必须留在 BLOCK。

### 10.3 三档策略实测

同一套语料、同一个归一化配置,只换策略文件:

| 策略 | ALERT 规则 | 变形未拦截 | **正常样本误拦截** | 误报(写 ALERT) |
|---|---|---|---|---|
| P0 全 BLOCK(改造前) | 0 | 6.1% | **18.8%**(9/48) | 18.8% |
| P1 降 5 条(默认) | 5 | 6.1% | **4.2%**(2/48) | 18.8% |
| P2 降 7 条 | 7 | 6.1% | **0.0%**(0/48) | 18.8% |

三个关键读数:

1. **"变形未拦截"一列三个策略完全相同** —— 降级没有让任何一条攻击从"拦"
   变成"只告警"。不是假设,是测出来的(`最新漏报.md` 第三节的降级代价清单是 0 条)。
2. 误拦截从 9 条降到 2 条 → 0 条,而"误报(写 ALERT)"不变 —— 说明这些请求
   仍然被看见了,只是不再对用户返回 403。
3. 剩下那 2 条是:英文句子 `the union select committee`(命中 `SQL-001`)
   和 `file=../../docs/readme.md`(命中 `PAT-001`)。P2 把这两条规则也降了,
   所以归零。

### 10.4 为什么默认只降 5 条(P1),不降 7 条(P2)

P2 在这套语料上代价也是 0,但我没有选它,因为:

- `PAT-001`(`../`)是**唯一能单枪匹马拦住** `?file=../../config.php` 这类
  目录穿越的规则 —— 它命中的文件不是 `/etc/passwd`,没有其他规则兜底。
- 语料是白盒的、有限的,它证明不了"线上不会出现只命中这两条的攻击"。
- 这两类误报有更合适的解法:**白名单按路径放行**(`rules/allowlist.conf`
  的既有机制),而不是把规则本身降级。`../` 在下载接口里是攻击,在静态资源
  路径里是正常 —— 这个区别只有路径能表达。

一句话:**能用"更窄的判据"解决的,不要用"更松的处置"解决。**

### 10.5 一个容易被忽略的层次依赖

`verify.sh` 里那条自检载荷是 `?q=union%20select%201,2,3`(URL 编码的):

- `select` 已被降级成 ALERT,所以**原始文本那一遍只能看到 ALERT**;
- 归一化把 `%20` 还原成空格,`union select` 命中 `SQL-001`(BLOCK 级)→ 403。

也就是说:**这条自检能过,靠的是归一化把编码载荷"升级"成了 BLOCK 级命中。**
如果哪天为了省性能把 `SECGUARD_ENGINE_NORMALIZE=0`,这批编码攻击会从"拦"
掉到"只告警"。层与层之间不是独立的,改一层要看另一层。

### 10.6 门禁口径也跟着改了

原来的门禁看"误报率"(命中即算)。现在必须看**误拦截率**(真的返回 403),
否则把规则全降级成 ALERT 就能让门禁变绿 —— 那是假绿。
代码里 `--max-fp` 现在校验的是 `benign_block.rate()`。

## 九、面试怎么讲(五个问题)

**Q:你怎么知道你的 WAF 有用?**
先有尺子再谈有用。我建了 169 条标注语料,39 条基线必须全中(实测 100%),
82 条变形只统计"基线本来能拦住"的那部分当分母。这个约束保证漏报率不是刷出来的。

**Q:61% 这个数字可靠吗?**
分两层看:**"这类变形族存在且原引擎全瞎"这件事是确定的**,因为它是代码读出来的
(未解码)+ 实测复现的。但"线上漏报率就是 61%"不成立 —— 语料是我按已知手法构造的
白盒语料,不是从真实攻击日志采样的。所以对外我只说"在这套语料上"。

**Q:为什么不直接上正则/语义分析?**
正则解决不了"等价语法"(or 1=1 vs or 2>1),语义分析要 AST 和上下文,
成本和延迟都不是一个量级。我的定位是:把**编码层**的绕过吃干净,
这部分是确定性的、可解释的、几乎零误报增量的;语法层留给下一代。

**Q:误报涨了 2 个点,凭什么说值得?**
因为 9 条误报里 8 条是存量问题,归一化只贡献 1 条(解码后 `<input>` 被标签规则命中)。
而且这 1 条指向真正的修法:标签规则要分"危险标签"和"普通 HTML"两级。
另外归一化把误报也变**可归因**了 —— 以前 `%3Cinput` 根本不会命中,没人知道这条规则会误伤。

**Q:为什么不干脆把那几条误报规则删了?**
删了就永远看不见那类流量了。我改成把处置降级:规则还在、命中还记、AI 分析还能用,
只是不返回 403。拆开之后误拦截从 18.8% 降到 4.2%,攻击拦截一条没少 —— 这个"没少"
是测出来的(降级代价清单 0 条),不是拍脑袋。设计细节见第十节。

**Q:这个改动对线上性能到底有多大影响?**
两层答案。引擎级:**+0.37 µs/请求**。端到端:**测不出来** —— 对照组和实验组
的变化符号相反、幅度都在 ±2.5% 噪声内。按单请求约 660 µs CPU 算,检测占 0.09%。
我不会说"性能零损耗",准确说法是"**在端到端指标上无法分辨**",这两句不一样。

**Q:最有意思的坑是哪个?**
行注释那次。我按"SQL 注释等价于空白"把 `--` 也剥了,结果 `order by 1--`
这类规则在规范形里永远命中不了,而且只有那一条变形漏报,其他都好了 ——
特别像"偶发 bug"。最后结论是:归一化只能还原,不能删除信息。这条比功能本身值钱。
