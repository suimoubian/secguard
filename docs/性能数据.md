# SecGuard 性能数据

两部分:**引擎微基准**(单次匹配多快)和**系统压测**(端到端能扛多少)。
两者都要有 —— 只报微秒级数字,读者不知道整套系统能撑多少 QPS;
只报 QPS,又看不出核心算法的价值。

数据都是本机实测。**本机是笔记本 + WSL2,抖动很大**(同一场景两轮能差 40%),
所以关键数字给了多轮结果与中位数,并标注了取数方式。

---

## 一、引擎微基准:AC 自动机 vs 朴素逐串匹配

```
机器     : 13th Gen Intel Core i7-13650HX
编译     : Release (-O2)
文本长度 : 2079 字节
每档迭代 : 2000 次取平均
```

| 特征数 | 节点数 | AC(微秒) | 朴素(微秒) | 加速比 |
|---|---|---|---|---|
| 200 | 1837 | 4.71 | 50.19 | **10.6x** |
| 500 | 4158 | 4.61 | 129.71 | **28.1x** |
| 1000 | 7807 | 4.96 | 260.15 | **52.5x** |

**特征数 ×5,AC 耗时 ×1.05,朴素 ×5.18。**

这正是 O(n+m) 与 O(n×k) 的差别:AC 把"同时匹配 1000 条规则"压缩成一次扫描,
朴素版要为每条规则各扫一遍文本。特征库越大,差距越大。

AC 稳态吞吐约 **20 万次/秒**(单次匹配,不含 HTTP 与落库)。

复现:

```bash
./build/ac_test 10000     # 正确性:15000 次随机对拍,零不一致
./build/ac_bench 2000 2048
```

## 二、系统压测:端到端 QPS

```
工具     : wrk 4.1.0
机器     : i7-13650HX(20 核),但**服务绑在 2 个核上**
           (taskset -c 0,1,模拟目标服务器的 2 核 4G)
压测端   : 另外 4 个核
每场景   : 10 秒,64 连接,keep-alive
服务配置 : 线程 64(见下面的"线程数"一节,为什么必须这样配)
```

### 2.1 完整链路

| 场景 | QPS | P50 | P99 |
|---|---|---|---|
| `GET /?q=hello`(完整检测链路) | **36520** | 1.57ms | **8.29ms** |
| `POST /api/check`(纯检测) | 28477 | 2.02ms | 11.20ms |
| `GET /?q=<2KB 文本>` | 16849 | 2.61ms | 11.25ms |
| `GET /?q=union select 1`(命中即拦) | 13338 | 4.32ms | 10.86ms |
| `GET /health`(每个请求 ping 一次 DB) | 10177 | 6.25ms | 23.16ms |
| `POST /api/login`(PBKDF2 12 万轮) | 44.93 | 135.80ms | 175.77ms |

"完整链路"指每个请求都走:Redis 封禁检查 + 令牌桶限流 → 234 条特征匹配 →
**写一条审计日志**(异步队列,最终落 MySQL)。

读法:

- **2 核能到 3.6 万 QPS,P99 8.3ms** —— 这是在"每个请求都落库审计"的前提下。
- 长文本(2KB)掉到 1.7 万:这是 AC 的 O(n) 部分在抬头,符合预期。
- 被拦截路径(13.3k)比放行路径慢:命中后要多写一次 Redis 命中计数,且响应是 403。
- `/health` 只有 1 万,因为它每个请求都真去 ping 一次数据库 —— 这是刻意的,
  健康检查必须验证"数据库通不通",不能只回一句 200。
- 登录 45 QPS **不是缺陷,是设计**:PBKDF2 12 万轮故意算得慢,
  让爆破不划算。代价是登录接口必须单独限流(V5 已做)。

### 2.2 异步审计队列值多少

| 配置 | QPS | P50 | P99 |
|---|---|---|---|
| 无锁队列 + 后台批量落库(默认) | **36520** | 1.57ms | 8.29ms |
| 同步写库(每个请求等一次 INSERT) | **281** | 200.27ms | 997.02ms |

**130 倍。** 这是整个项目里单项收益最大的一处设计。

道理也简单:写库是毫秒级,匹配是微秒级。同步写库等于让每个请求都去排数据库的队。

### 2.3 Redis 分布式状态值多少

| 配置 | QPS | P50 | P99 |
|---|---|---|---|
| 有 Redis(限流/封禁跨实例共享) | 36520 | 1.57ms | 8.29ms |
| 关掉 Redis(退回单机内存) | 49766 | 1.09ms | 18.22ms |

差 1.36 倍 —— 这是"正确性"的成本。单机版更快,但多实例部署时每个实例各限各的,
限额被放大 N 倍,等于没限。这笔账必须付,能做的是把成本压小(见第三节)。

> 注:优化前这个差距是 **2.8 倍**(20627 vs 57828),因为那时每请求要两次
> Redis 往返、且每次都抢连接池的全局锁。第三节是把它压下来的过程。

### 2.4 服务线程数(并发 64 不变)

| 线程数 | QPS | P50 | P99 |
|---|---|---|---|
| 4 | 13376 | 533us | **437.82ms** |
| 16 | 24254 | 662us | 154.10ms |
| 32 | 30763 | 1.25ms | 108.98ms |
| **64** | 31377 | 1.80ms | **9.87ms** |

**httplib 的 keep-alive 是"一个线程守一条连接"。** 线程数少于并发连接数时,
多出来的连接在队列里干等,表现就是 **QPS 不变、P99 爆十几倍**。

这是本次压测最有价值的一条运维结论:线程数要跟预期并发连接数对齐,
否则你看到的延迟根本不是服务端处理时间。

### 2.5 登录:PBKDF2 迭代轮数的成本

| 迭代轮数 | QPS | P50 |
|---|---|---|
| 1 万 | 180 | 32.90ms |
| 12 万(默认) | 45 | 135.80ms |

轮数 ×12,吞吐掉到 1/4。默认值 12 万是安全与成本的折中:
攻击者爆破一个口令要付的代价,和我们正常登录要付的代价,是同一条曲线上的两个点。

## 三、压测驱动的三次优化

这一节是整个过程里最值得讲的部分 —— 数字不是一开始就好看的。

### 3.1 起点

| | QPS | P99 |
|---|---|---|
| 初版 | 20627 | 15ms |

### 3.2 优化一:线程数对齐并发数

`SECGUARD_THREADS=4` 配 64 连接 → 60 条连接在排队。

改成 64 后:P99 从 **348ms 降到 9.25ms**,QPS 不变。

> 结论:先在配置上把模型用对,再谈代码优化。

### 3.3 优化二:合并两次 Redis 往返

原来每请求两次:封禁检查 `EXISTS` + 令牌桶 `EVALSHA`。
封禁检查本身就是只读的,直接并进令牌桶的 Lua 脚本里:

```lua
if redis.call('EXISTS', KEYS[2]) == 1 then return -1 end   -- 封禁中
... 令牌桶计算 ...
return ok
```

验证方式(不受机器噪声影响):用程序内的 `redis_commands / requests_total` 比值。

```
合并前: 2.00 次往返/请求
合并后: 1.00 次往返/请求
```

### 3.4 优化三:每线程一条 Redis 连接

合并后吞吐还是上不去。一次 loopback 往返不该值 30 微秒 ——
真正贵的是 **64 个线程每次请求都要抢同一把连接池锁两次**(借、还)。

改成每线程缓存一条连接(线程退出时归还),热路径上完全不碰锁:

| | QPS | P99 |
|---|---|---|
| 优化前 | 20627 | 15ms |
| 优化后 | **35070** | **7.68ms** |

**吞吐 +70%,P99 减半。**

### 3.5 这里踩到的坑

改成每线程连接之后,单元测试**卡死在 `futex_do_wait`**。

原因:线程局部缓存的连接由 `thread_local` 析构函数归还,
但 TLS 析构发生在线程退出时 —— 若 `RedisClient` 此时已销毁,
归还动作就会去锁一个已销毁的 mutex。

服务端没暴露这个问题(工作线程在 client 之前 join 了),
单元测试里两者都在主线程上,一跑就卡。

修法:维护一张"存活客户端"登记表,析构前先摘牌;
TLS 析构时先查表,查不到就把连接直接丢掉(不再调用已销毁对象)。

> 这类问题的价值在于:**它不会崩,只会挂住**,而且只在特定生命周期下复现。

## 四、另一个压测副作用:审计表会涨到失控

跑完几轮压测后再看库:

```
audit_log: 3,241,444 行,584 MB
```

3 分钟压测写了 320 万行。这暴露了一个真实的生产问题:
**审计表是"每请求一行",不清理就会吃光磁盘**,而且越到后面删除越慢。

已加保留策略:`SECGUARD_AUDIT_RETENTION_DAYS`(默认 7 天),
后台每 10 分钟删一批(带 `LIMIT`,避免巨型 DELETE 把库锁住)。

## 五、这些数字怎么用

写简历/讲项目时,建议这样组合:

```
单机 2 核:C++ 实现的多模式匹配引擎,234 条特征下
完整检测链路 3.6 万 QPS、P99 8.3ms(含每请求审计落库);
核心匹配算法相比朴素逐串匹配在 1000 条特征时快 52 倍
```

三个数字对应三件事:系统能力(3.6 万)、延迟保证(P99 8.3ms)、算法价值(52 倍)。

## 六、已知局限(讲的时候要主动说)

- 本机是笔记本 + WSL2,**绝对数字会与真实服务器有差异**(尤其 P99)。
  上线后应在目标机器上重跑 `bench/run.sh` 复核。
- 压测走 loopback,没有真实网络栈的损耗;真实公网 RTT 会显著抬高 P99。
- 只压了单机。多实例横向扩展没测(Redis 已经是共享的,理论上可线性扩)。
- 登录场景的并发很低(c=8),因为它本来就被限流保护;
  若按 c=64 压,测到的是队列而不是 PBKDF2。

## 七、W9 复测:绝对数字不可靠,比值才可靠

上线前又完整跑了一遍(代码比 W7 多了管理鉴权、白名单、请求体检测)。
同一台机器、同一个脚本,结果差距很大:

| 场景 | W7 记录 | W9 复测 | 差异 |
|---|---|---|---|
| 完整检测链路 | 36520 | 56371 | +54% |
| 长文本 2KB | 16849 | 33011 | +96% |
| 命中即拦 | 13338 | 14733 | +10% |
| /api/check | 28477 | 50871 | +79% |
| /health | 10177 | 14417 | +41% |
| 登录(12 万轮) | 44.93 | 70.75 | +57% |

**代码没有任何加速。** W9 加的全是检查和鉴权,只可能更慢。
差异来源是机器状态:笔记本的 CPU 睿频、WSL2 的内存回收、
后台是否还有别的进程 —— 同一场景两轮差 40% 在我这台机器上是常态。

### 所以对外该报哪个数

**报保守的那个(W7 的数字)**,并说明理由:

> "我这台笔记本上同一场景跑两轮能差 40%,所以我引用的是多次测量里的下界。
> 真实数字要在云服务器上重测。"

这比挑一个好看的数字写在简历上安全得多 —— 面试官真要你去他机器上跑,
报高了的那个数字撑不住。

### 真正稳定的东西:比值

绝对值飘,但**同一轮内的比例关系是稳的**,这也是更值得讲的结论:

| 对比 | W7 | W9 |
|---|---|---|
| 异步审计 vs 同步写库 | 130x | **194x**(56371 vs 291) |
| Redis 共享限流 vs 单机内存 | 1.36x | **1.50x**(56371 vs 84654) |
| 线程 64 vs 线程 4 | — | **2.6x**(52369 vs 20673),P99 从 289ms 降到 6ms |
| PBKDF2 12 万轮 vs 1 万轮 | — | **3.8x**(70.75 vs 267.88) |

这四组说的是同一件事:**每个设计决定值多少**,而且不受机器状态影响。
面试时讲这些比背 QPS 数字有说服力。
